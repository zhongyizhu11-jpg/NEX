# FXP 抗丢包传输（lossTolerant）设计说明

隧道上的一个可选项，默认关，按隧道开。开了以后，入口 / 中转到下一跳的**承载连接**从 TCP 换成
UDP 上的 KCP + Reed-Solomon 前向纠错；承载之上的一切（握手、AEAD 帧、多路复用、连接池、多路径、
流量统计）不动。代码：`loss_carrier.go`（连接、封包、关闭 / 复位 / 保活）、`loss_carrier_dial.go`
（拨号）、`loss_carrier_listen.go`（监听）。

## 现状（改之前）

- **承载**：入口 → [中转 …] → 出口，每一跳都是 TCP。每条用户 TCP 连接对应一条承载 TCP 连接
  （`selected_transport.go`，从 `endpoint_pool.go` 的预热池取，或现拨 + 流水线握手）。
- **握手和帧**（`main.go` / `aead.go` / `frame_reader.go`）：客户端 salt + 握手帧，服务端回自己的 salt +
  确认；会话密钥由两边 salt 派生，AES-256-GCM 或 ChaCha20-Poly1305 协商。帧 = 加密的 4 字节长度 +
  加密的内容，按计数做 nonce。这一层只要求一个可靠、有序的字节流（`net.Conn`）。
- **多腿**（`multipath*.go`）：单连接叠加 / 多路并发 / 复制 / 热备，都是在入口把一条用户连接拆到
  几条承载连接（每条一样经 `dialSecureTCP`）上，出口按序号重组。
- **UDP 业务流量**：不走承载连接，走 UDP 直连（`udp_direct.go`，每包独立 AEAD，`FXPU` 包头），可选
  `udp_fec.go` 的逐跳纠错（「UDP 抗丢包」，只管 UDP）。UDP 直连监听和 TCP 监听同号（用 mimic 时另配端口）。
- **配置流**：面板 `tunnels` 表的列 → 心跳里 `applyForwardXTransport`（`server/agentHeartbeatRoute.ts`，
  入口、中转、出口的 FXP 规格都经过它）→ Agent `fxpSpec`（`agent/main.go`，原样 JSON 写成 FXP 配置，
  签名变了热更新 / 重启）→ FXP `config`（`config_types.go`），运行时按配置指纹逐个监听比对（`runtime_manager.go`）。

问题：跨境线路晚高峰常有几个百分点的随机丢包。TCP（cubic，BBR 也受影响）把丢包当拥塞，窗口收缩，
单连接跑不起来，而且丢一个段后面的数据全部排队等重传（队头阻塞），交互延迟一抖就是几百毫秒。

## 方案：在帧 / AEAD 之下换承载

`dialNextHop` 是唯一的分叉点：关着时就是原来的 `dialTCP`；开了只拨 `dialLossCarrier`。监听侧在 TCP 监听
的同一个端口号上加一个 UDP 承载监听，接进来的连接交给同一个处理器、同一套连接登记和闸门。

- **KCP**（`github.com/xtaci/kcp-go/v5` v5.6.72，纯 Go）：选择重传、快速重传（被跳过 2 次即重发）、
  最小重传超时 30 ms、**关掉拥塞窗口**（丢包不降速 —— 抗丢包的主要来源），窗口固定 1024 段。
- **FEC**：10 个数据包配 3 个冗余包（kcp-go 自带的 Reed-Solomon），一组里丢 3 个以内不用等重传。
- **补上 KCP 没有的**：OPEN / OPEN-ACK 建连（对端答了才算连上，连不上当场报错）、逐包认证
  （ChaCha20-Poly1305 只认证不加密，16 字节，密钥按会话由隧道密钥 + 两边随机数派生；内容本来就是
  上层 AEAD 的密文，不再加密一遍）、FIN / FIN-ACK（写完就关时尾巴照样送到，读到 EOF 才算完）、
  PING / PONG 保活（5 s，顺带保 NAT 映射）、45 s 失联判死、对端不认识会话时回 RESET（重启后旧池子
  里的连接立刻作废）。包头 `FXPK`，和 `FXPU` / `FXPF` 不撞，所以能和 UDP 直连共用一个 UDP 端口：
  UDP 直连的读循环把认不出的 `FXPK` 包转交过来（没开这个模式的隧道只多一次 4 字节比较，而且只发生在
  本来就要丢的包上）；那个端口上没有 UDP 直连（只跑 TCP、或用 mimic 另配了端口）时运行时单独起一个只
  收承载包的读循环。

**为什么不是 QUIC（quic-go）**：QUIC 没有 FEC；它对丢包的改进是丢包恢复更准（RACK、按包号不歧义）和
多流之间没有队头阻塞 —— 但 FXP 一条用户连接本来就是一条承载，单流内照样队头阻塞；它的拥塞控制
（Cubic / Reno）遇到随机丢包一样收窗口，正是我们要躲开的。再加上 quic-go 依赖面大（qpack、x/net 一串）、
新版本要更高的 Go 版本，而且它自带 TLS 1.3，和 FXP 自己的握手重复。KCP 关拥塞窗口 + FEC 直接针对
「随机丢包不是拥塞」这个场景。

**依赖和兼容性**：kcp-go v5.6.73 起要求 Go 1.25，v5.7 要 1.26；v5.6.72 是最后一个 `go 1.24.0` 的版本，
go.mod 的 `go 1.24.0` 不抬。新增 kcp-go、pkg/errors、tjfoc/gmsm（kcp-go 的 SM4 加密，链进来但不用）、
x/net v0.49.0、x/time。去掉符号的二进制：amd64 8.63 → 9.00 MB（+0.35 MB），arm64 7.14 → 7.54 MB（+0.39 MB）。
govulncheck（CI 的 Go 1.26 + v1.9.0）：代码可达的漏洞 0；x/net v0.49.0 有几条模块级（代码没调用）
的公告，修好的版本（≥ v0.52）都要求 Go ≥ 1.25，抬不了。

## 严格模式

- 入口 / 中转开了就只拨 UDP 承载。对端 UDP 口没人听（ICMP 顶回来两次）立刻报 refused；没人答
  （防火墙丢、对端没开、对端是旧版本、密钥不对）按拨号超时报 no answer。错误进日志、进端点健康
  （`exit endpoint unhealthy … reason=loss-tolerant transport: …`），连接监控里是单独一个阶段
  「抗丢包连接」，最近一次失败原因写着哪种情况。不退回 TCP。
- 出口 / 中转开了以后，从 TCP 进来、握手通过的会话一律不接（限频日志：上一跳 FXP 旧了或者还没拿到
  新配置）。否则一端升级了、一端没升级时会「以为开了，其实走的 TCP」。
- V2（WireGuard）不支持：外层已经是 UDP。面板不下发，FXP 配置校验也拒。

## 线上要开的端口

出口和每台中转：**入站 UDP，端口号 = 这一跳的隧道 TCP 端口**（TCP 端口照旧要开，监听还在，只是开了
这个模式后不接 TCP 会话）。没开 mimic 的 NEX 隧道本来就要放行同号 UDP（UDP 直连），不用多开；开了
mimic 的隧道要额外放行这个 UDP 端口（mimic 只伪装它自己的端口，承载包是明文包头的 UDP）。入口只往外拨，
每条承载连接一个临时 UDP 源端口，不用开端口。面板的防火墙模块本来就不管隧道出口 / 中转端口
（`server/ops/firewallStore.ts`），和现在一样由用户在安全组里放行。

## 和聚合 / 热备腿的共存

多路径的每条腿都经 `dialSecureTCP` → `dialSecureTCPFresh` → `dialNextHop`，开了就每条腿各一条 UDP 承载；
中转（并排中转）也按同一个开关监听。重组、复制、热备、丢腿重传都在承载之上，不受影响。端点状态
（健康、预热池）按「地址 + 密钥 + 承载方式」区分，同一出口的 TCP 连接和 UDP 承载不会混进一个池子。
热备腿空闲时每 5 s 一个 PING。

## 验证（`loss_carrier_*_test.go`）

进程内有损网络（`loss_carrier_net_test.go`）：包在拨号方 UDP 套接字外面，两个方向各自独立随机丢包、
加延迟和抖动（抖动不超车）、按比例乱序。

- `TestLossCarrierKeepsDataIntactUnder{Five,Fifteen}PercentLoss`：6 MB 双向同时传，sha256 一致，实测丢包
  5.1% / 15.2%。线上字节 / 有效字节：5% 时 1.48、15% 时 1.70（含冗余包、重传、确认）。
- `TestLossTolerantTunnelCarriesTrafficEndToEndUnderLoss`：真实运行时 + 握手 + 帧加密，入口 → 出口，
  5% / 15% 丢包下 3 条并发连接各 3 MB 回声，校验和一致、连接不断；`…ThroughRelay`：入口 → 中转 → 出口，
  出口 both（和 UDP 直连共用端口）。
- 严格模式：出口没开 → 入口不退回 TCP 且错误写明原因；出口开了 → 不接 TCP 上游；热更新开关 UDP 监听；
  写完就关时 15% 丢包下尾巴不丢；伪造来源不建会话、回 RESET；对端重启后旧连接立刻报 reset。
- `go test -race` 过。

## 基准（`loss_carrier_bench_test.go`，4 核共享机器，入口和出口在同一进程里，CPU 是两端合计）

**进程内有损网络**（单向 10 ms ± 4 ms，3% 乱序 +15 ms，往返约 24 ms），抗丢包承载，单条连接：

| 丢包 | 单连接 Mbit/s | 4 条连接合计 | 64 B 一问一答 p50 / p90 / p99 / 最大（ms） |
| --- | --- | --- | --- |
| 0（只有延迟） | 356 | 1264 | 26.3 / 28.7 / 41.9 / 61 |
| 1% | 311 | 1116 | 26.5 / 29.2 / 71 / 138 |
| 5% | 227 | 812 | 26.6 / 42.0 / 139 / 995 |
| 15% | 117–141 | 368 | 27.2 / 158 / 917 / 5218 |

TCP 没法放进这个有损网络（内核里的 TCP 不经过我们的套接字），所以这张表没有 TCP 对照。单连接速率受
固定窗口封顶：1024 段 × 1323 B ≈ 1.35 MB，≈ 1.35 MB ÷ 往返时间（200 ms 的线路约 54 Mbit/s）。

**同一种内核级丢包下和 TCP 比**：网络命名空间里只对隧道中间那一段（出口端口的 TCP 和 UDP，两个方向）
用 `iptables -m statistic --mode random` 丢包，lo 的 MTU 1500、GSO 关掉（不然 TCP 一个 64 KB 的段只算
一个包）。没有 netem，**往返时间约等于 0** —— 这对 TCP 是最有利的条件（重传几乎立刻发生），真实线路上
TCP 会差得多。拥塞控制 BBR。单条连接：

| 丢包 | TCP Mbit/s | 抗丢包 Mbit/s | TCP 一问一答 p90 / p99 | 抗丢包 p90 / p99 |
| --- | --- | --- | --- | --- |
| 0 | 444 | 615 | — | — |
| 1% | 183 | 567 | — | — |
| 5% | 14.1 | 396 | 208 / 434 ms | 0.41 / 87 ms |
| 15% | 3.4（2 分钟传不完 32 MB，改传 4 MB） | 262 | 304 / 748 ms | 86 / 427 ms |

**没有丢包时的代价**（普通回环，有 GSO，不经有损网络）：单连接 TCP 13 978 Mbit/s、1.7 CPU 秒 / GB；
抗丢包 2 004–2 222 Mbit/s、11.4–11.7 CPU 秒 / GB —— **每 GB 的 CPU 约 6.7 倍**（两端合计；KCP 每个
1.3 KB 包一次封包 / 认证 / 系统调用，TCP 有 GSO/GRO 一次搬 64 KB），64 B 一问一答 p50 从 0.012 ms 到
0.15 ms（KCP 20 ms 时钟之外的固定开销）。流量多 30%（冗余包）再加 2–3% 包头。也就是说：线路不丢包时
开它只有坏处。

**没模拟的**：成串丢包（真实线路常见，3/10 的纠错能力挡不住一串，要靠重传）；运营商对 UDP 的限速 /
QoS（晚高峰有的线路 UDP 比 TCP 丢得更狠）；带宽限速器造成的丢包（关了拥塞窗口会一直撞上去，这种线路
应该用链路整形，手动档对承载照样生效，自动档靠 TCP_INFO 认不出 UDP 承载）。都没在真实跨境线路上测过。

## 发布注意

- 需要隧道上**所有主机的 Agent 和 FXP 都升级**：Agent 不认识 `lossTolerant` 会在写 FXP 配置时丢掉它，
  FXP 不认识就当没开。版本号由协调者定。
- 两端不一致时：入口新、出口旧 → 入口拨 UDP 没人答，这条隧道的 TCP 流量不通，连接监控里「抗丢包连接」
  失败写着原因；入口旧、出口新 → 出口拒收 TCP 会话，FXP 日志里有 `refused tcp session … upstream
  outdated`。都不会悄悄退回 TCP。建议面板保存时按版本拦（还没做）。
- 开关切换时：先拿到新配置的一端和还没拿到的一端之间有最多一个心跳周期的中断（严格模式的代价）。
- 关着的隧道：FXP / Agent 配置 JSON、签名、监听计划、线上字节都和以前一模一样，不多开套接字。唯一的
  常驻开销是 kcp-go 包初始化时起的 NumCPU + 1 个调度协程（阻塞等任务，不占 CPU，几 KB 栈）。
