# NEX V3 性能对比

基线是**移植原样**：提交 18ebfe861 的 FXP（它和移植提交 7d2460ce9 相比，FXP 只改了版本号和
「改 V3 外层选项不重启 UDP 直连监听」，数据面一个字节没动，基本就是上游的实现）。优化后是本分支
的 FXP。两边跑的是同一份 `forwardx-fxp/bench_v3_test.go`（只用 config 字段起隧道，原样拷到基线
提交上就能跑）。

## 怎么跑

```sh
cd forwardx-fxp
# 回环吞吐：三种外层 × 复用开 / 关，和 V1 对照
go test -run '^$' -bench 'BenchmarkV3Bulk$' -benchtime 300x -count 3 .
# 带往返延迟（延迟代理 50ms / 200ms）、短连接、首连；每个子项跑 V3BENCH_SECONDS 秒（默认 4）
go test -run '^$' -bench 'BenchmarkV3(BulkRTT|ConnRate)' -benchtime 1x -count 2 .
go test -run '^$' -bench 'BenchmarkV3FirstConn' -benchtime 5x .
# V1 / V2 的数据面回归（bench_dataplane_test.go，改动前后各跑一遍）
go test -run '^$' -bench 'BenchmarkDataplaneTCP(Bulk|RTT)' -count 3 .
# 内层 AEAD 两种算法（模式 3 AES-128-GCM / 模式 5 ChaCha20-Poly1305）：只测算法、整条隧道
go test -run '^$' -bench 'BenchmarkInnerAEAD' -count 3 ./internal/v3/
go test -run '^$' -bench 'BenchmarkV3InnerCipher' -benchtime 300x -count 3 .
# 同样两条命令前面加 GODEBUG=cpu.aes=off：模拟没有 AES 硬件（标准库 AES 退回纯 Go 实现）
```

测基线：`git worktree add /tmp/base 18ebfe861`，把 `bench_v3_test.go` 拷进
`/tmp/base/forwardx-fxp/`，同样的命令跑一遍。

## 环境和怎么读

- 4 vCPU 的 Xeon 2.1 GHz 虚拟机（共享宿主），Go 1.24.7，全部在本机回环上，入口、出口（和延迟代理）
  在同一个进程里。cpu-ms/GB 是整个进程（两端 + 夹具）的 CPU。
- 这台机器有噪声：同一份 V1 代码两次运行能差 20% 以上（见下面每张表里的 V1 行）。所以吞吐表
  另给了「相对同一次运行里的 V1」一列，这一列不受机器快慢影响。
- **延迟代理**（`v3BenchDelayProxy`）：每个方向读到的字节过 RTT/2 再写给对面，补上 TCP 三次握手
  那一个往返；不限带宽，每个方向最多 32 MiB 在路上。所以：
  - 不复用、单连接、200ms 往返时，上限是 32 MiB / 100 ms ≈ 2.68 Gbit/s（链路本身的上限，不是
    隧道的）；
  - 2 Gbit/s 以上的读数基本是代理（同一个进程里的拷贝）在吃 CPU，看的是数量级；
  - 复用时卡住吞吐的是每条流的窗口：窗口 / 往返时延。移植原样每流 64 KiB，50ms 下 ≈10 Mbit/s、
    200ms 下 ≈2.6 Mbit/s，实测一致。
- 短连接：16 个并发客户端，每个循环「拨号 → 发 64 字节 → 等回声 → 关」，p50 / p99 是从拨号到收到
  回声。首连：隧道起来 1.5 秒后（还没有任何用户连接）的第一条连接。

## 做了什么（按贡献从大到小）

| 改动 | 主要影响 |
| --- | --- |
| 复用的每流窗口自适应（BLOCKED 信号，128 KiB → 16 MiB，会话 / 进程预算） | 高延迟线路上复用单流 2.5 → 480 Mbit/s（200ms） |
| 隐含初始窗口（开流不等额度） | 复用短连接、首连少一个往返 |
| 内层记录层：读缓冲 + 就地解密，一批一次封、一次系统调用 | 不复用吞吐 1.8–2.6×，分配降 75–90% |
| 多路复用写协程批量写、帧缓冲 / 收包块走池、帧 64 KiB、额度攒够才发 | 复用吞吐 3.8–5.6×，分配降 90% 以上 |
| TLS 1.3 外层时内层直通（模式 4） | TLS 的 CPU/GB 再降一截，内层握手不占往返 |
| 内层握手一个往返（服务端证明随材料一起回） | 不复用、预热池没命中时少一个往返 |
| 复用时预热会话、快满时后台再备一条 | 复用首连 310 → 54 ms（50ms 往返） |
| HTTP / WS 请求头、回应和内层第一条消息拼段 | 少几个 TCP 段 |

### 内层 AEAD 算法：AES-128-GCM vs ChaCha20-Poly1305（模式 3 / 5）

模式 3 / 5 按两端有没有 AES 硬件自动选（协商见 `PROTOCOL.md`「内层算法协商」）；这里比两种算法的
代价。这台机器有 AES-NI，「没有 AES 硬件」用 `GODEBUG=cpu.aes=off` 模拟：标准库的 AES 退回纯 Go
的查表实现（和没有加密扩展的 ARM 上 Go 走的是同一份代码），ChaCha20 的汇编不受影响。
`BenchmarkV3InnerCipher` 用 `v3.OverrideAESHardware` 让两端都当作有 / 没有 AES 硬件，从而强制协商出
某一种算法；TLS 外层是模式 4（内层直通），不在这张表里。

只测算法（`BenchmarkInnerAEAD`：单核把一条 16 KiB 的记录封好再解开，含 2 字节长度的那次密封，
-count 3 中位数；cpu-ms/GB 是「封 + 解」1 GB 明文的单核 CPU）：

| 本机 | AES-128-GCM | ChaCha20-Poly1305 | ChaCha20 / AES 的 CPU |
| --- | --- | --- | --- |
| 有 AES-NI | 2,698 MB/s · 370 cpu-ms/GB | 877 MB/s · 1,141 cpu-ms/GB | 3.1×（ChaCha20 更贵） |
| `cpu.aes=off`（没有 AES 硬件） | 58 MB/s · 17,232 cpu-ms/GB | 947 MB/s · 1,056 cpu-ms/GB | 0.061×（AES-GCM 贵 16×） |

整条隧道（`BenchmarkV3InnerCipher`，回环、入口和出口在一个进程里，cpu-ms/GB 是整个进程；
有 AES 时 -benchtime 300x，`cpu.aes=off` 时只跑不复用、-benchtime 100x，都是 -count 3 中位数）：

| 路径 | 连接 | 有 AES-NI：AES-GCM | 有 AES-NI：ChaCha20 | 没有 AES：AES-GCM | 没有 AES：ChaCha20 |
| --- | --- | --- | --- | --- | --- |
| v3-ws-nomux | 1 | 9.74 Gbps · 2,365 | 6.44 Gbps · 3,366 | 0.70 Gbps · 25,110 | 5.20 Gbps · 3,700 |
| v3-ws-nomux | 4 | 13.7 Gbps · 2,152 | 11.1 Gbps · 2,797 | 1.37 Gbps · 20,680 | 8.83 Gbps · 2,890 |
| v3-http-nomux | 1 | 9.73 Gbps · 2,279 | 5.49 Gbps · 3,586 | 0.65 Gbps · 25,440 | 5.30 Gbps · 3,614 |
| v3-http-nomux | 4 | 15.7 Gbps · 1,961 | 10.8 Gbps · 2,893 | 1.18 Gbps · 23,400 | 8.07 Gbps · 3,033 |
| v3-ws-mux | 1 | 8.18 Gbps · 2,937 | 6.54 Gbps · 3,573 | - | - |
| v3-ws-mux | 4 | 10.0 Gbps · 2,629 | 6.70 Gbps · 3,599 | - | - |
| v3-http-mux | 1 | 8.86 Gbps · 2,686 | 6.21 Gbps · 3,688 | - | - |
| v3-http-mux | 4 | 10.3 Gbps · 2,667 | 6.78 Gbps · 3,716 | - | - |

怎么读：

- 有 AES 硬件时 ChaCha20 整条隧道的 CPU/GB 多 20–60%（每 GB 多约 0.6–1.3 秒 CPU，和只测算法时「封 + 解」
  一次的差 0.77 秒同一个量级），吞吐低 20–45%。所以两端都有 AES 硬件时仍用 AES-GCM。
- 没有 AES 硬件时纯 Go 的 AES-GCM 是瓶颈：整条隧道 CPU/GB 是 ChaCha20 的 6.8–7.7 倍，吞吐只有
  ChaCha20 的 12–16%。选 ChaCha20 后，「没有 AES」的机器上 V3 的 HTTP / WS 外层吞吐接近有 AES-NI 时
  用 ChaCha20 的水平（单连接 5.2 vs 6.4 Gbps）。
- 只要有一端没有 AES 硬件就用 ChaCha20：有硬件的那端多花的是上面第一条的那 20–60%，没有硬件的那端
  省下的是 6–7 倍。

ARM 上的预期（**没有在 ARM 上实测**）：

- 带 ARMv8 加密扩展的 ARM（AWS Graviton、Ampere Altra、苹果 M 系列、多数云厂商的 ARM 实例，以及
  Cortex-A53 / A55 / A72 等带加密选项的芯片）：x/sys/cpu 报有 AES + PMULL，照旧用 AES-GCM，表现和
  上面「有 AES-NI」那两列同一类。
- 没有加密扩展的 ARM（树莓派 3 / 4 的 BCM2837 / BCM2711、一些便宜的 ARM 小鸡、32 位 ARM）：Go 的
  AES-GCM 走纯 Go 查表实现，和这里 `cpu.aes=off` 的 AES-GCM 列是同一份代码；ChaCha20 在 arm64 上有
  NEON 汇编（Poly1305 是纯 Go），在 32 位 arm 上两者都是纯 Go。按 x86 上软件实现的比例（只测算法 16×、
  整条隧道 6–7×）和这类小核的特点，预期 ChaCha20 的吞吐是 AES-GCM 的数倍，绝对值受限于单核速度，
  通常远低于这里的 Gbps 级数字。要实测：在那台机器上跑上面两条基准命令（不用 GODEBUG）。
- 32 位 arm、386、riscv64 等架构这里一律当作没有 AES 硬件（Go 1.24 的 AES-GCM 在这些架构上没有汇编）。

## 结论和局限

- 回环吞吐：不复用的 V3 从同次 V1 的 34–47% 提到 85–100%，复用的从 14–16% 提到 61–90%（4 条流共用一条
  物理连接时，上限是一条 TCP 的写协程）。CPU/GB 降 44–76%，分配降 75–95%。TLS 外层直通之后，
  TLS 不再比 WS / HTTP 贵。
- 高延迟：复用的单条流 200ms 往返下 2.5 → 约 490 Mbit/s（16 MiB 窗口的理论上限是 671 Mbit/s，
  测量窗口里还带着几个往返的爬坡），50ms 下 10 → 约 1.9 Gbit/s。不复用的单连接本来就只受 TCP
  限制，和 V1 一样贴着延迟代理的上限。
- 短连接：复用时每条新连接少一个往返（50ms 往返下 p50 105 → 53 ms，每秒连接数翻倍）；不复用时
  预热池命中时本来就只要一个往返，没命中时（p99）少一个往返：TLS p99 262 → 158 ms。
- 首连：复用时规则一起来就预热好会话，310 / 258 → 约 54 ms（和不复用、V1 一样只剩一个往返）。
- 内层 AEAD 按两端 AES 硬件选算法：两端都有 AES 硬件时不变（AES-GCM）；任意一端没有时改用
  ChaCha20-Poly1305，模拟没有 AES 硬件时整条隧道（HTTP / WS 外层、不复用）吞吐约 6–8 倍、CPU/GB 降 85%
  以上。ARM 上的数字没有实测。
- 延迟代理是进程内的、不丢包、不限带宽；丢包、带宽上限下的表现见下一节「丢包 + 高延迟线路」。
  没有做多机、长时间的压测。

## 丢包 + 高延迟线路（linksim）

上面的数字都是本机回环、不丢包。跨境线路的真实问题是丢包 + 高延迟：多路复用时所有逻辑流挤在一条
TCP 上，一个包丢了大家一起等重传（队头阻塞）。这一节在模拟的丢包线路上量 V1、V3 不复用、V3 复用，
优化前后对比。

### 环境：linksim

开发机内核没有 netem（`tc qdisc add ... netem` 报 Specified qdisc kind is unknown），所以自己做了
一条用户态线路 `forwardx-fxp/internal/linksim`（只给测试 / 基准用，用法见它的 main.go 开头）：

```
nexsim-a (10.231.0.1)  ──TUN──  linksim  ──TUN──  nexsim-b (10.231.0.2)
压测客户端 + FXP 入口          延迟 / 丢包 / 限速          FXP 出口 + 目标服务
```

- 两个网络命名空间各一块 TUN，A 侧内核发往 B 的每个 IP 包都从 TUN 读出来，在用户态按设定处理后
  写进另一侧的 TUN。两端是真实的内核 TCP，重传、BBR、接收窗口、发送队列都是真的。
- 线路：每个方向 200 Mbit/s 瓶颈，瓶颈队列一个 BDP（排队超过一个往返就尾丢）；往返 50 ms / 200 ms；
  每个方向各自随机丢包 0% / 0.5% / 2%（ACK 也丢）。Go 的定时器精度在 1 ms 上下，包大约 1 ms 一批放出。
- 命名空间里的 TCP 设置照着 Agent 安装脚本的网络调优：BBR、`tcp_rmem` / `tcp_wmem` 上限 64 MB、
  `tcp_notsent_lowat` 128 KiB、`tcp_slow_start_after_idle` 0 等。这台机器的内核没有 fq，BBR 用自己的
  发包节奏。FXP 本身对 cubic / reno 默认的机器会按连接换 BBR（tcp_congestion.go），V1、V3 都一样，
  所以这里所有路径都是 BBR。
- 起真实的 forwardx-fxp 进程：出口在 nexsim-b、入口在 nexsim-a；V3 外层都是 TLS（内层直通）；链路
  整形关（面板默认）。数据方向是下载：目标服务 → 出口 → 线路 → 入口 → 客户端。
- 负载（`linksim load`）：
  - **bulk**：1 / 4 / 16 条流一直下载，去掉前 3 秒，报后 7 秒的总速率（Mbit/s）。
  - **fixed**：每轮 4 / 16 条流同时各下载 2 MiB，记每条流从拨号到收完的时间；每个点 5 轮摊平，
    报 p50 / p90 / 最大（ms）。看多路复用的队头阻塞。
  - **rpc**：1 条流一直下载，3 秒后（下载已经跑起来）另开一条连接每 20 ms 一问一答 64 字节，报 7 秒
    里往返的 p50 / p99（ms），括号里是同时那条下载的速率。看交互流量被大流量拖慢多少。
  - **rpc-shared**：先开一问一答的连接、紧接着开下载（复用时两条在同一条会话上），其余同 rpc。
- 每个点跑 3 次：bulk 取中位数，fixed / rpc 的样本摊平取分位数。「V3 复用 优化后」之外的三列是
  同一批优化前的数据：V1 和 V3 不复用的代码这一轮没有动。

```sh
cd forwardx-fxp
go build -o /tmp/fxp . && go build -o /tmp/linksim ./internal/linksim
sudo /tmp/linksim bench -fxp /tmp/fxp -label after -out /tmp/r.jsonl -runs 3
/tmp/linksim report -labels before,after /tmp/before.jsonl /tmp/r.jsonl
# 只量复用、只量一部分：
sudo /tmp/linksim bench -fxp /tmp/fxp -label x -out /tmp/x.jsonl -rtts 200 -losses 2 -paths v3-mux -tests bulk,rpc
```

**噪声**：200 ms + 丢包时 BBR 的启动阶段偶尔会过早结束（按 `ss -ti` 看到的：启动阶段有一段被接收窗口
卡住，带宽估计停在几 Mbit/s 就进了 ProbeBW，之后每 8 个往返只涨 25%），这条 TCP 接下来十几秒只有
几 Mbit/s 到几十 Mbit/s。V1、V3 不复用的新连接也会碰到（优化前的数据里 V3 不复用一次 9 Mbit/s、
一次 25 Mbit/s）。所以 200 ms 丢包的那几行，3 次的中位数之间差 10–20 Mbit/s 不说明问题；表里只把
明显的塌方单独注出来。

### 优化前看到的问题

1. **吞吐**：200 Mbit/s 的线路上，0.5%、2% 丢包时 V1、V3 不复用、V3 复用基本都跑得满——BBR 不把随机
   丢包当拥塞。复用单流在 200 ms 往返、不丢包时反而只有 184（V1 201），而且每次瓶颈队列都丢 15–16%
   的包（V1 是 0–5%）。
2. **复用时交互流量很慢**：一条下载跑着时，同一会话里的一问一答 50 ms 往返下 p50 676 ms、200 ms 往返下
   839 ms（V1、不复用 87 / 205 ms），不丢包也一样。这不是网络上的排队（瓶颈队列最多一个往返），
   `ss -tin` 看出口那条会话的 TCP：`notsent` 好几 MB 到十几 MB。原因：
   - 内核把发送缓冲自动放大到 `tcp_wmem` 上限（64 MB），复用窗口又会放大到 16 MiB，下载的数据大半堆在
     这条 TCP 的发送队列里，交互流量的小包排在它们后面。命名空间里 `tcp_notsent_lowat` 设了 128 KiB，
     但在这个内核上那个 sysctl 没有限住发送队列（同一个值按连接设的 `TCP_NOTSENT_LOWAT` 才管用：
     单独的测试程序里 sysctl 时 `notsent` 43 MB，按连接设了是 0.1 MB）。
   - 窗口卡住发送时，底下那条 TCP 是 app-limited 的；BBR 的启动阶段只在不是 app-limited 的往返里判断
     带宽到顶，于是一直停在 2.89 倍增益（`ss` 里 `pacing_gain:2.88672`、`cwnd` 约 2.9 倍 BDP），
     瓶颈队列被灌满——这就是上面 15% 的丢包，丢了又让会话里所有流一起等重传。
3. **窗口自适应会不会过度放大**：会，但放大的部分涨进的是发送端的发送队列（上一条），不是网络。
   200 ms 往返时 16 MiB 又不够 BBR 用（要盖住「在途量 + 额度回来的半个往返 + 额度粒度」，约 3.5 倍 BDP，
   200 Mbit/s × 200 ms 是 17.5 MB），才有第 2 条里卡在启动阶段的事。

### 做了什么

| 改动 | 依据 |
| --- | --- |
| 复用会话的物理连接两端按连接设 `TCP_NOTSENT_LOWAT` = 128 KiB（v3_session.go，只复用的会话；不复用的连接上只有一条流，不设） | 下面「发送队列上限」的实验（32 MiB 窗口、所有流挤一条会话）：挤在一起的交互往返 736 → 93 ms（50 ms 往返）、1375 → 214 ms（200 ms 往返），吞吐不变；回环上 8 Gbit/s 量级的吞吐也不变 |
| 每流窗口上限 16 → 32 MiB，会话预算 32 → 64 MiB（进程预算 256 MiB 不变） | 200 ms 往返不丢包时，复用单流瓶颈队列丢包 15–16% → 0–6%，吞吐 184 → 193–200；顺带回环 + 延迟代理（`BenchmarkV3BulkRTT`，不丢包、不限带宽）复用单流 50 ms 1.9 → 4.9 Gbit/s、200 ms 484 → 1,190 Mbit/s |
| 额度攒够窗口的四分之一才还，但最多攒 1 MiB | 窗口几十 MiB 时四分之一是好几 MiB，额度一大块一大块地回来，发送队列中间见底（又是 app-limited）；1 MiB 时 200 Mbit/s 下一秒二十几个额度帧，开销可以不计 |

线格式没变（额度帧本来就能任意大小；窗口由接收端放大，发送端只要求累计额度不超过 64 MiB，新旧两端
混用也通）。

**试过、没有采用：把流分到多条会话上**。会话池记每条会话最近的流量，有大流量在跑的会话不再放新流，
新流放到不忙的会话上（没有就后台再备一条，一个端点最多 4 条）。交互流量确实不再等别人的重传
（rpc：200 ms / 2% 下 p50 202 ms，和不复用一样），但在丢包线路上吞吐变差：多出来的会话都是新的 TCP，
要从启动阶段爬起，而上面说的「启动阶段过早结束」在新连接上碰得更多；一条会话的 BBR 估计塌了之后
闲着不跑数据也恢复不了，下一次挑中它又是几 Mbit/s。同一批测试里 200 ms / 0.5%、2% 时 rpc / rpc-shared
里那条下载的中位数掉到 18–139 Mbit/s（不分流 169–191），fixed 16 条流的最大完成时间 5.3–5.9 秒
（不分流 2.9–3.3 秒）。分流的代码没有合进来（量过两种挑法：不忙的会话里挑空位最多的、挑累计流量最多的，
结果差不多），
复用时的队头阻塞留着，丢包线路上要低延迟的交互流量就别开复用（面板默认本来就不开）。

### 结论和建议

- **交互流量**（这一轮最大的问题）：复用时下载跑着，一问一答从 676–839 ms 降到 94–213 ms（不丢包，和
  V1、不复用一样）；丢包时 118–585 ms，还是比 V1 / 不复用的 54–203 ms 高——这部分是一条 TCP 上的
  队头阻塞，复用本身绕不开。
- **吞吐**：200 Mbit/s 的线路上所有路径基本都跑得满，复用没有因为丢包吃亏；200 ms 不丢包时复用单流
  184 → 193，瓶颈队列不再被自己灌满（15% → 0–6% 丢包）。
- **多流完成时间**（fixed）：复用的最大完成时间都比不复用、V1 短，p50 多数也更短（会话的 TCP 是热的，
  不用每条流各自爬坡；50 ms 丢包、16 条流时 p50 略长）。优化后比优化前分布更窄：最大值多数降了，
  p50 有的格子略高。
- **V1 / V3 不复用**在丢包线路上一样，这一轮没有动它们的代码。V1 的 TCP 已经按连接设 BBR
  （tcp_congestion.go，auto 时把 cubic / reno 换成 bbr）。
- **多路复用的默认值**：建议保持默认关。不复用在丢包线路上的吞吐、交互延迟都和 V1 一样；复用的好处
  是建连快（少一个往返）、物理连接少、多条流的完成时间短，代价是丢包时交互流量要等别人的重传。
  适合「很多短连接、单条流量小」的用法，或者线路基本不丢包的时候。
- **建议（要改 Agent 的网络调优，V1 也受影响；后来量完采用了 1 MiB，见下一节「tcp_rmem 起点」）**：把
  `net.ipv4.tcp_rmem` 的中间值（每条连接接收缓冲的起点）从内核默认的 128 KiB 抬到 1–4 MiB（只量了 4 MiB）。它只是起点，缓冲按实际收到的
  数据才占内存，空闲连接不多占；好处是高延迟丢包线路上新连接的 BBR 不再被接收窗口卡住、过早结束
  启动阶段。另外，同一台机器上 `net.ipv4.tcp_notsent_lowat` 这个 sysctl 没有限住发送队列（按连接设
  才管用），Agent 调优里的那一项可能在别的内核上也不生效，没有深查。
- 没覆盖到的：真实的跨境线路（丢包常常是成串的，不是这里的独立随机丢包）、乱序、抖动、比 200 Mbit/s
  更高的带宽、长时间运行；BBR 只有 v1（内核里没有 bbr2 / bbr3）。

## tcp_rmem 起点（Agent 网络调优，影响 V1 / V2 / V3）

上一节的「噪声」里看到：200 ms + 丢包时，新连接的 BBR 启动阶段偶尔被接收窗口卡住、过早结束，之后十几秒
只有几到几十 Mbit/s。接收窗口从 `net.ipv4.tcp_rmem` 的中间值（每条 TCP 接收缓冲的起点）开始，按每个往返
应用读走的量往上长；Agent 的网络调优（agent/ext_nettune.go、安装脚本 apply_network_tuning）原来只抬
上限（64 MB），起点是内核默认的 128 KiB。这是整机的 sysctl：V1、V2（内核数据面）、V3 隧道，gost、realm
这些用户态转发的每条 TCP 都从它起步。这一节对比起点 128 KiB / 1 MiB / 4 MiB。

**结论：起点抬到 1 MiB（已改：Agent 2.2.257 的一键调优和安装脚本，只抬不降），不用 4 MiB。**

- 1 MiB：200 ms 丢包线路上新连接「塌掉」从 13/120 次降到 3/120；多条流一起下载（16 条 × 2 MiB）一轮收完的
  时间 V1、V2 短 12–18%（V3 不复用短 2–7%，复用持平）；交互往返、稳态吞吐、不丢包和 50 ms 线路上都没有
  可分辨的变差。
- 4 MiB：起步更快（200 ms 丢包时前 5 秒的平均 V1 / V2 / V3 不复用比 128 KiB 高 10–85%），塌掉 1/120；但
  50 ms + 0.5% 丢包时 16 条新连接同时下载，最慢那条 V1 晚 12%、V2 晚 14% 收完（30 轮，Mann-Whitney
  p = 0.018 / 0.008），对端读得慢的连接最多攒的数据也是 1 MiB 的 4 倍。不满足「延迟和带宽都不变差」。

### 方法

- 线路、命名空间里的 TCP 设置、FXP 进程、负载的协议都和上一节一样（linksim，200 Mbit/s 瓶颈，队列一个
  BDP，往返 50 / 200 ms × 每个方向独立随机丢包 0 / 0.5 / 2%，BBR）；只改两个命名空间里
  `net.ipv4.tcp_rmem` 的中间值（`4096 <起点> 67108864`）。另有一组 1 Gbit/s（只量 200 ms / 0.5%）。
- **V2**：开发机内核没有 wireguard 模块，用一个 wireguard-go 驱动内核 TUN 的小程序（agent/internal/wgsim，两端
  `nexsim-wa` / `nexsim-wb`，10.232.0.1 / .2，走 linksim 那条线）代替内核 WireGuard，FXP 以
  `transportVersion: "v2"` 跑在 WireGuard 地址上（明文帧），和 Agent 的内核直通数据面一样：隧道里是
  内核 TCP，BBR、tcp_rmem 都生效，只是加解密在用户态（单流比 V1 低 5% 左右，是这台机器的 CPU）。
  没有内核 wireguard 模块时 Agent 用 gVisor 用户态协议栈（netstack 数据面），它不读内核的 tcp_rmem
  （自己的接收缓冲起点本来就是 1 MiB，见 agent/wireguard_netstack_tuning.go），这一节的改动对它没有影响。
- `linksim rmem`（rmem_linux.go）：每个链路设定下，每一轮、每种路径把三个候选值轮流设进去（每轮换一个
  起点，抵消先后顺序和旁边联调环境每 3 分钟一轮回归带来的 CPU 噪声），每个值都重起一对 FXP（新的 TCP、
  新的复用会话），依次跑：
  - **ramp**：一条新连接从拨号起下载 20 秒，每 500 ms 记一格：前 5 秒、前 15 秒的平均，最后 5 秒（稳态）。
    **塌**：前 15 秒平均低于带宽的 30%。
  - **rpc**：同上一节（下载跑起来 3 秒后另开一问一答，7 秒的往返 p50 / p99）。不复用时那条下载也是新
    连接，它第 3–10 秒的速率低于带宽 30% 也记一次塌。
  - **fixed**：每轮 16 条流同时各下载 2 MiB，记一轮全部收完的时间（最慢那条）和单条流完成时间的 p50。
- 次数：每个点 5 次，表里是中位数（rpc 是每次的 p50 / p99 再取中位数）。200 ms 丢包的 ramp 补到 10 次；
  50 ms 丢包的 fixed 补到 30 轮；V1、V3 复用的 rpc 在 0 / 2% 丢包时补到 15 次；1 Gbit/s 各 5 次。差别是不是噪声用 Mann-Whitney U（双侧）看。

```sh
cd forwardx-fxp
go build -o /tmp/fxp . && go build -o /tmp/linksim ./internal/linksim
(cd ../agent && go build -o /tmp/wgsim ./internal/wgsim)   # 只有路径里有 v2 时要
sudo /tmp/linksim rmem -fxp /tmp/fxp -wg /tmp/wgsim -out /tmp/m.jsonl -runs 5
sudo /tmp/linksim rmem -fxp /tmp/fxp -wg /tmp/wgsim -out /tmp/g.jsonl -rate 1000 -rtts 200 -losses 0.5
/tmp/linksim rmem-report /tmp/m.jsonl /tmp/g.jsonl
```

### 起点大了为什么多流反而慢（4 MiB、50 ms 丢包）

单条流完成时间的 p50 三者一样（1.47–1.54 秒），差在尾巴：50 ms 丢包时 16 条里第 90 百分位那条，V1 / V2
128 KiB、1 MiB 都是 1.87–2.14 秒，4 MiB 2.06–2.18 秒（晚 5–10%），最慢那条晚 10–20%。推测是：起点
128 KiB / 1 MiB 时，每条新连接头几个往返被接收窗口限着，16 条加起来的在途量不会一下子冲过瓶颈队列；
4 MiB 时窗口不再限，16 个 BBR 启动阶段一起按 2.89 倍增益灌，50 ms 线路的队列只有 1.25 MB（一个 BDP），
丢在最后几个包上的连接要等超时重传。这条没有查实：瓶颈队列的丢包 V2 多了 6–10%，V1 持平。200 ms 线路上
BDP 是 5 MB，这个效应被「启动不再被卡住」盖过去，4 MiB 反而最快。1 MiB 两头都不吃亏。

### 内存：对端读得慢时最坏多占多少

接收缓冲是按收到的数据分配的，没数据进来的连接不占；自动放大（`tcp_moderate_rcvbuf`）只在应用读走数据时
发生，所以**对端（本机的应用）一直不读**时，这条连接最多攒到起点为止。转发里这种情况很常见：下游客户端
慢（手机、限速），转发进程停下不读上游，上游那条 TCP 的接收队列就会攒满；上游是同机房的目标（往返很短）
时，它的缓冲本来不会自动长大，原来停在 128 KiB。

实测（`linksim up -rtt 2ms -rate 0`，nexsim-b 里跑 `linksim sink`，nexsim-a 里
`linksim load -mode hold -streams 200 -duration 12s`：200 条下载连上后接收端一个字节都不读，9 秒后看
`ss -tm` 的 `skmem r`，按 skb 实际占的内存算，含包头开销）：

| 起点 | 每条连接攒的内存 | 其中数据（Recv-Q） | 200 条合计 |
| --- | --- | --- | --- |
| 128 KiB | 167 KiB | 105 KiB | 33 MiB |
| 1 MiB | 1.04 MiB | 668 KiB | 208 MiB |
| 4 MiB | 3.9 MiB | 2.4 MiB | 777 MiB |

所以每条「对端不读」的连接最坏比原来多占：1 MiB 约 0.9 MiB，4 MiB 约 3.7 MiB。整机 TCP 内存受
`net.ipv4.tcp_mem` 管（内核按内存大小自动设，大约是内存的 4.7% / 6.2% / 9.4%，单位是页）：超过第二个值
进入压力模式，所有连接的窗口都被压小；超过第三个值新到的数据直接丢。按「只有这一种内存」粗算，到压力线
要多少条一直不读的连接：

| 机器内存 | tcp_mem 压力线 | 128 KiB | 1 MiB | 4 MiB |
| --- | --- | --- | --- | --- |
| 1 GB | ≈ 62 MB | ≈ 380 条 | ≈ 60 条 | ≈ 16 条 |
| 4 GB | ≈ 250 MB | ≈ 1,500 条 | ≈ 240 条 | ≈ 64 条 |
| 16 GB（这台：255408 页 ≈ 1 GB） | ≈ 1 GB | ≈ 6,000 条 | ≈ 960 条 | ≈ 256 条 |

（实测 4 MiB × 200 条时 `/proc/net/sockstat` 的 TCP mem 涨了 27 万页（含发送端），已经过了这台机器
tcp_mem 的压力线 25.5 万页。）这是最坏情况：读得慢但在读的连接，攒的量受它的速率限制，远到不了起点；跑得快的连接本来就会
自动放大到几 MB（上限 64 MB 没变）。1 MiB 时多出来的量比一条跑满的 200 ms 跨境连接自动放大后的缓冲（几 MB 到十几 MB）
还小；小内存、几百上千条并发慢连接的机器要留意，可以在「网络调优 › 逐项设置」里把起点改回 131072。

### 对 V1 / V2 / V3 的影响

- **V1、V3 不复用、V2（内核数据面）**：每条业务连接一条隧道 TCP，都是新连接，受益最多：200 ms 丢包线路上
  塌掉的少了，多流下载更早收完。
- **V3 复用**：业务连接是会话里的逻辑流，物理 TCP 只在会话建立时爬一次坡，起点只影响新会话的第一段；
  表里复用的差别都在噪声里（1 Gbit/s 多流 1 MiB 短一些，p ≈ 0.05）。交互往返（rpc）三种起点一样，上一节的发送队列上限照样管用。
- **V2 用户态数据面（netstack）**：不受内核 sysctl 影响，没变。
- 不丢包、50 ms 线路：三种起点没有可分辨的差别。

### 没覆盖到的

- 真实跨境线路（成串丢包、乱序、抖动）、比 1 Gbit/s 更高的带宽、长时间运行；BBR 只有 v1。
- V2 是 wireguard-go + 内核 TUN 模拟的内核数据面，没有在真的内核 WireGuard 上量。
- gost、realm 没有单独量（它们的 TCP 一样从这个起点起步，按 V1 的结果推）。
- 内存只量了「完全不读」的最坏情况，没有在小内存机器上压到 tcp_mem 压力线看实际表现。
