# NEX V3 性能对比

基线是**移植原样**：提交 18ebfe861 的 FXP（它和移植提交 7d2460ce9 相比，FXP 只改了版本号和
「改 V3 外层选项不重启 UDP 直连监听」，数据面一个字节没动，基本就是上游的实现）。优化后是本分支
的 FXP。两边跑的是同一份 `forwardx-fxp/bench_v3_test.go`（只用 config 字段起隧道，原样拷到基线
提交上就能跑）。

## 怎么跑

```sh
cd forwardx-fxp
# 回环吞吐：三种外层 × 复用开 / 关，和 V1 对照
go test -run '^$' -bench 'BenchmarkV3Bulk$' -benchtime 300x -count 3 .
# 带往返延迟（延迟代理 50ms / 200ms）、短连接、首连；每个子项跑 V3BENCH_SECONDS 秒（默认 4）
go test -run '^$' -bench 'BenchmarkV3(BulkRTT|ConnRate)' -benchtime 1x -count 2 .
go test -run '^$' -bench 'BenchmarkV3FirstConn' -benchtime 5x .
# V1 / V2 的数据面回归（bench_dataplane_test.go，改动前后各跑一遍）
go test -run '^$' -bench 'BenchmarkDataplaneTCP(Bulk|RTT)' -count 3 .
```

测基线：`git worktree add /tmp/base 18ebfe861`，把 `bench_v3_test.go` 拷进
`/tmp/base/forwardx-fxp/`，同样的命令跑一遍。

## 环境和怎么读

- 4 vCPU 的 Xeon 2.1 GHz 虚拟机（共享宿主），Go 1.24.7，全部在本机回环上，入口、出口（和延迟代理）
  在同一个进程里。cpu-ms/GB 是整个进程（两端 + 夹具）的 CPU。
- 这台机器有噪声：同一份 V1 代码两次运行能差 20% 以上（见下面每张表里的 V1 行）。所以吞吐表
  另给了「相对同一次运行里的 V1」一列，这一列不受机器快慢影响。
- **延迟代理**（`v3BenchDelayProxy`）：每个方向读到的字节过 RTT/2 再写给对面，补上 TCP 三次握手
  那一个往返；不限带宽，每个方向最多 32 MiB 在路上。所以：
  - 不复用、单连接、200ms 往返时，上限是 32 MiB / 100 ms ≈ 2.68 Gbit/s（链路本身的上限，不是
    隧道的）；
  - 2 Gbit/s 以上的读数基本是代理（同一个进程里的拷贝）在吃 CPU，看的是数量级；
  - 复用时卡住吞吐的是每条流的窗口：窗口 / 往返时延。移植原样每流 64 KiB，50ms 下 ≈10 Mbit/s、
    200ms 下 ≈2.6 Mbit/s，实测一致。
- 短连接：16 个并发客户端，每个循环「拨号 → 发 64 字节 → 等回声 → 关」，p50 / p99 是从拨号到收到
  回声。首连：隧道起来 1.5 秒后（还没有任何用户连接）的第一条连接。

## 做了什么（按贡献从大到小）

| 改动 | 主要影响 |
| --- | --- |
| 复用的每流窗口自适应（BLOCKED 信号，128 KiB → 16 MiB，会话 / 进程预算） | 高延迟线路上复用单流 2.5 → 480 Mbit/s（200ms） |
| 隐含初始窗口（开流不等额度） | 复用短连接、首连少一个往返 |
| 内层记录层：读缓冲 + 就地解密，一批一次封、一次系统调用 | 不复用吞吐 1.8–2.6×，分配降 75–90% |
| 多路复用写协程批量写、帧缓冲 / 收包块走池、帧 64 KiB、额度攒够才发 | 复用吞吐 3.8–5.6×，分配降 90% 以上 |
| TLS 1.3 外层时内层直通（模式 4） | TLS 的 CPU/GB 再降一截，内层握手不占往返 |
| 内层握手一个往返（服务端证明随材料一起回） | 不复用、预热池没命中时少一个往返 |
| 复用时预热会话、快满时后台再备一条 | 复用首连 310 → 54 ms（50ms 往返） |
| HTTP / WS 请求头、回应和内层第一条消息拼段 | 少几个 TCP 段 |

## 结论和局限

- 回环吞吐：不复用的 V3 从同次 V1 的 34–47% 提到 85–100%，复用的从 14–16% 提到 61–90%（4 条流共用一条
  物理连接时，上限是一条 TCP 的写协程）。CPU/GB 降 44–76%，分配降 75–95%。TLS 外层直通之后，
  TLS 不再比 WS / HTTP 贵。
- 高延迟：复用的单条流 200ms 往返下 2.5 → 约 490 Mbit/s（16 MiB 窗口的理论上限是 671 Mbit/s，
  测量窗口里还带着几个往返的爬坡），50ms 下 10 → 约 1.9 Gbit/s。不复用的单连接本来就只受 TCP
  限制，和 V1 一样贴着延迟代理的上限。
- 短连接：复用时每条新连接少一个往返（50ms 往返下 p50 105 → 53 ms，每秒连接数翻倍）；不复用时
  预热池命中时本来就只要一个往返，没命中时（p99）少一个往返：TLS p99 262 → 158 ms。
- 首连：复用时规则一起来就预热好会话，310 / 258 → 约 54 ms（和不复用、V1 一样只剩一个往返）。
- 延迟代理是进程内的、不丢包、不限带宽；丢包、带宽上限下的表现见下一节「丢包 + 高延迟线路」。
  没有做多机、长时间的压测。

## 丢包 + 高延迟线路（linksim）

上面的数字都是本机回环、不丢包。跨境线路的真实问题是丢包 + 高延迟：多路复用时所有逻辑流挤在一条
TCP 上，一个包丢了大家一起等重传（队头阻塞）。这一节在模拟的丢包线路上量 V1、V3 不复用、V3 复用，
优化前后对比。

### 环境：linksim

开发机内核没有 netem（`tc qdisc add ... netem` 报 Specified qdisc kind is unknown），所以自己做了
一条用户态线路 `forwardx-fxp/internal/linksim`（只给测试 / 基准用，用法见它的 main.go 开头）：

```
nexsim-a (10.231.0.1)  ──TUN──  linksim  ──TUN──  nexsim-b (10.231.0.2)
压测客户端 + FXP 入口          延迟 / 丢包 / 限速          FXP 出口 + 目标服务
```

- 两个网络命名空间各一块 TUN，A 侧内核发往 B 的每个 IP 包都从 TUN 读出来，在用户态按设定处理后
  写进另一侧的 TUN。两端是真实的内核 TCP，重传、BBR、接收窗口、发送队列都是真的。
- 线路：每个方向 200 Mbit/s 瓶颈，瓶颈队列一个 BDP（排队超过一个往返就尾丢）；往返 50 ms / 200 ms；
  每个方向各自随机丢包 0% / 0.5% / 2%（ACK 也丢）。Go 的定时器精度在 1 ms 上下，包大约 1 ms 一批放出。
- 命名空间里的 TCP 设置照着 Agent 安装脚本的网络调优：BBR、`tcp_rmem` / `tcp_wmem` 上限 64 MB、
  `tcp_notsent_lowat` 128 KiB、`tcp_slow_start_after_idle` 0 等。这台机器的内核没有 fq，BBR 用自己的
  发包节奏。FXP 本身对 cubic / reno 默认的机器会按连接换 BBR（tcp_congestion.go），V1、V3 都一样，
  所以这里所有路径都是 BBR。
- 起真实的 forwardx-fxp 进程：出口在 nexsim-b、入口在 nexsim-a；V3 外层都是 TLS（内层直通）；链路
  整形关（面板默认）。数据方向是下载：目标服务 → 出口 → 线路 → 入口 → 客户端。
- 负载（`linksim load`）：
  - **bulk**：1 / 4 / 16 条流一直下载，去掉前 3 秒，报后 7 秒的总速率（Mbit/s）。
  - **fixed**：每轮 4 / 16 条流同时各下载 2 MiB，记每条流从拨号到收完的时间；每个点 5 轮摊平，
    报 p50 / p90 / 最大（ms）。看多路复用的队头阻塞。
  - **rpc**：1 条流一直下载，3 秒后（下载已经跑起来）另开一条连接每 20 ms 一问一答 64 字节，报 7 秒
    里往返的 p50 / p99（ms），括号里是同时那条下载的速率。看交互流量被大流量拖慢多少。
  - **rpc-shared**：先开一问一答的连接、紧接着开下载（复用时两条在同一条会话上），其余同 rpc。
- 每个点跑 3 次：bulk 取中位数，fixed / rpc 的样本摊平取分位数。「V3 复用 优化后」之外的三列是
  同一批优化前的数据：V1 和 V3 不复用的代码这一轮没有动。

```sh
cd forwardx-fxp
go build -o /tmp/fxp . && go build -o /tmp/linksim ./internal/linksim
sudo /tmp/linksim bench -fxp /tmp/fxp -label after -out /tmp/r.jsonl -runs 3
/tmp/linksim report -labels before,after /tmp/before.jsonl /tmp/r.jsonl
# 只量复用、只量一部分：
sudo /tmp/linksim bench -fxp /tmp/fxp -label x -out /tmp/x.jsonl -rtts 200 -losses 2 -paths v3-mux -tests bulk,rpc
```

**噪声**：200 ms + 丢包时 BBR 的启动阶段偶尔会过早结束（按 `ss -ti` 看到的：启动阶段有一段被接收窗口
卡住，带宽估计停在几 Mbit/s 就进了 ProbeBW，之后每 8 个往返只涨 25%），这条 TCP 接下来十几秒只有
几 Mbit/s 到几十 Mbit/s。V1、V3 不复用的新连接也会碰到（优化前的数据里 V3 不复用一次 9 Mbit/s、
一次 25 Mbit/s）。所以 200 ms 丢包的那几行，3 次的中位数之间差 10–20 Mbit/s 不说明问题；表里只把
明显的塌方单独注出来。

### 优化前看到的问题

1. **吞吐**：200 Mbit/s 的线路上，0.5%、2% 丢包时 V1、V3 不复用、V3 复用基本都跑得满——BBR 不把随机
   丢包当拥塞。复用单流在 200 ms 往返、不丢包时反而只有 184（V1 201），而且每次瓶颈队列都丢 15–16%
   的包（V1 是 0–5%）。
2. **复用时交互流量很慢**：一条下载跑着时，同一会话里的一问一答 50 ms 往返下 p50 676 ms、200 ms 往返下
   839 ms（V1、不复用 87 / 205 ms），不丢包也一样。这不是网络上的排队（瓶颈队列最多一个往返），
   `ss -tin` 看出口那条会话的 TCP：`notsent` 好几 MB 到十几 MB。原因：
   - 内核把发送缓冲自动放大到 `tcp_wmem` 上限（64 MB），复用窗口又会放大到 16 MiB，下载的数据大半堆在
     这条 TCP 的发送队列里，交互流量的小包排在它们后面。命名空间里 `tcp_notsent_lowat` 设了 128 KiB，
     但在这个内核上那个 sysctl 没有限住发送队列（同一个值按连接设的 `TCP_NOTSENT_LOWAT` 才管用：
     单独的测试程序里 sysctl 时 `notsent` 43 MB，按连接设了是 0.1 MB）。
   - 窗口卡住发送时，底下那条 TCP 是 app-limited 的；BBR 的启动阶段只在不是 app-limited 的往返里判断
     带宽到顶，于是一直停在 2.89 倍增益（`ss` 里 `pacing_gain:2.88672`、`cwnd` 约 2.9 倍 BDP），
     瓶颈队列被灌满——这就是上面 15% 的丢包，丢了又让会话里所有流一起等重传。
3. **窗口自适应会不会过度放大**：会，但放大的部分涨进的是发送端的发送队列（上一条），不是网络。
   200 ms 往返时 16 MiB 又不够 BBR 用（要盖住「在途量 + 额度回来的半个往返 + 额度粒度」，约 3.5 倍 BDP，
   200 Mbit/s × 200 ms 是 17.5 MB），才有第 2 条里卡在启动阶段的事。

### 做了什么

| 改动 | 依据 |
| --- | --- |
| 复用会话的物理连接两端按连接设 `TCP_NOTSENT_LOWAT` = 128 KiB（v3_session.go，只复用的会话；不复用的连接上只有一条流，不设） | 下面「发送队列上限」的实验（32 MiB 窗口、所有流挤一条会话）：挤在一起的交互往返 736 → 93 ms（50 ms 往返）、1375 → 214 ms（200 ms 往返），吞吐不变；回环上 8 Gbit/s 量级的吞吐也不变 |
| 每流窗口上限 16 → 32 MiB，会话预算 32 → 64 MiB（进程预算 256 MiB 不变） | 200 ms 往返不丢包时，复用单流瓶颈队列丢包 15–16% → 0–6%，吞吐 184 → 193–200；顺带回环 + 延迟代理（`BenchmarkV3BulkRTT`，不丢包、不限带宽）复用单流 50 ms 1.9 → 4.9 Gbit/s、200 ms 484 → 1,190 Mbit/s |
| 额度攒够窗口的四分之一才还，但最多攒 1 MiB | 窗口几十 MiB 时四分之一是好几 MiB，额度一大块一大块地回来，发送队列中间见底（又是 app-limited）；1 MiB 时 200 Mbit/s 下一秒二十几个额度帧，开销可以不计 |

线格式没变（额度帧本来就能任意大小；窗口由接收端放大，发送端只要求累计额度不超过 64 MiB，新旧两端
混用也通）。

**试过、没有采用：把流分到多条会话上**。会话池记每条会话最近的流量，有大流量在跑的会话不再放新流，
新流放到不忙的会话上（没有就后台再备一条，一个端点最多 4 条）。交互流量确实不再等别人的重传
（rpc：200 ms / 2% 下 p50 202 ms，和不复用一样），但在丢包线路上吞吐变差：多出来的会话都是新的 TCP，
要从启动阶段爬起，而上面说的「启动阶段过早结束」在新连接上碰得更多；一条会话的 BBR 估计塌了之后
闲着不跑数据也恢复不了，下一次挑中它又是几 Mbit/s。同一批测试里 200 ms / 0.5%、2% 时 rpc / rpc-shared
里那条下载的中位数掉到 18–139 Mbit/s（不分流 169–191），fixed 16 条流的最大完成时间 5.3–5.9 秒
（不分流 2.9–3.3 秒）。分流的代码没有合进来（量过两种挑法：不忙的会话里挑空位最多的、挑累计流量最多的，
结果差不多），
复用时的队头阻塞留着，丢包线路上要低延迟的交互流量就别开复用（面板默认本来就不开）。

### 结论和建议

- **交互流量**（这一轮最大的问题）：复用时下载跑着，一问一答从 676–839 ms 降到 94–213 ms（不丢包，和
  V1、不复用一样）；丢包时 118–585 ms，还是比 V1 / 不复用的 54–203 ms 高——这部分是一条 TCP 上的
  队头阻塞，复用本身绕不开。
- **吞吐**：200 Mbit/s 的线路上所有路径基本都跑得满，复用没有因为丢包吃亏；200 ms 不丢包时复用单流
  184 → 193，瓶颈队列不再被自己灌满（15% → 0–6% 丢包）。
- **多流完成时间**（fixed）：复用的最大完成时间都比不复用、V1 短，p50 多数也更短（会话的 TCP 是热的，
  不用每条流各自爬坡；50 ms 丢包、16 条流时 p50 略长）。优化后比优化前分布更窄：最大值多数降了，
  p50 有的格子略高。
- **V1 / V3 不复用**在丢包线路上一样，这一轮没有动它们的代码。V1 的 TCP 已经按连接设 BBR
  （tcp_congestion.go，auto 时把 cubic / reno 换成 bbr）。
- **多路复用的默认值**：建议保持默认关。不复用在丢包线路上的吞吐、交互延迟都和 V1 一样；复用的好处
  是建连快（少一个往返）、物理连接少、多条流的完成时间短，代价是丢包时交互流量要等别人的重传。
  适合「很多短连接、单条流量小」的用法，或者线路基本不丢包的时候。
- **建议（要改 Agent 的网络调优，V1 也受影响，没有动）**：把 `net.ipv4.tcp_rmem` 的中间值（每条连接
  接收缓冲的起点）从内核默认的 128 KiB 抬到 1–4 MiB（只量了 4 MiB）。它只是起点，缓冲按实际收到的
  数据才占内存，空闲连接不多占；好处是高延迟丢包线路上新连接的 BBR 不再被接收窗口卡住、过早结束
  启动阶段。另外，同一台机器上 `net.ipv4.tcp_notsent_lowat` 这个 sysctl 没有限住发送队列（按连接设
  才管用），Agent 调优里的那一项可能在别的内核上也不生效，没有深查。
- 没覆盖到的：真实的跨境线路（丢包常常是成串的，不是这里的独立随机丢包）、乱序、抖动、比 200 Mbit/s
  更高的带宽、长时间运行；BBR 只有 v1（内核里没有 bbr2 / bbr3）。
