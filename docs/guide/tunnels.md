# 隧道链路

隧道连接入口与出口主机，适合跨主机转发、加密链路、多跳和多出口场景。

```text
用户 -> 入口 -> 隧道 -> 出口 -> 目标
```

配置入口：

```text
链路管理 -> 隧道
```

![隧道页面展示链路拓扑、类型和当前运行状态](./images/tunnels-overview.png)

## 隧道类型

| 类型 | 说明 |
| --- | --- |
| GOST | 使用 TLS、WSS、TCP、MTLS、MWSS 或 MTCP 等 GOST 模式 |
| NEX V1 | 使用 AES-256-GCM 认证加密的 FXP 传输 |
| NEX V2 | 外层使用 Agent 内置 userspace WireGuard，内层继续使用 FXP |
| Nginx Stream | 使用独立 Nginx 四层运行时，支持 TCP/UDP；TCP 可选 TLS 证书 |

## NEX V1 与 V2

| 版本 | 传输 | 兼容性 |
| --- | --- | --- |
| V1 | FXP AES-256-GCM TCP/UDP 加密通道 | 已有隧道继续使用 V1，不会自动切换 |
| V2 | userspace WireGuard 外层 UDP + FXP 内层 | 需要链路内 Agent 均满足界面要求的最低版本 |

V2 不依赖系统 `wg` 命令，不创建系统 WireGuard 网卡，也不修改系统路由。每个隧道在每台 Agent 上复用一套 WireGuard 运行时，规则通过本机回环代理接入。

V2 支持单跳、多跳、入口组、多出口、TCP/UDP、限速、PROXY Protocol 和链路测试。使用前确认所有节点的防火墙和安全组放行 WireGuard UDP 端口；端口可手动填写，留空时由面板分配。

## GOST

GOST 模式的物理承载和业务规则协议不是同一概念。TLS/WSS/TCP 等隧道承载通常监听 TCP，业务规则仍可按模式能力传输 TCP、UDP 或 TCP+UDP。面板和 Agent 的就绪检查以实际承载监听为准，不会要求不存在的 UDP 物理监听。

## Nginx Stream

Nginx 仅保留 Stream 模式：

- 支持 TCP、UDP 和 TCP+UDP 四层转发。
- TCP 可配置证书和私钥启用 TLS；UDP 不使用 TLS。
- 使用独立 `forwardx-nginx` 二进制、配置目录和服务。
- 监听隧道配置中的端口，不固定占用 80 端口。
- 适合出口组负载均衡，不等同于 NEX 自定义加密隧道。

隧道模式只接受当前的 `nginx_stream`。旧 `nginx_tls` 数据不再由运行时自动转换，跨版本升级时请先按[升级和备份](./upgrade-backup.md#跨兼容边界升级)执行一次性迁移。

## 多入口、多跳和多出口

- **多入口**：先创建入口组，再由隧道引用。
- **多跳**：按真实网络路径排列中继节点，并为每跳选择连接地址。
- **多出口**：先创建出口组（选好出口策略：主备 / 轮流 / 随机 / 按访客固定 / 按权重），再在隧道里引用。
- 连接地址留空时使用主机默认入口；也可指定内网 IP、IPv6 或域名。

使用出口组时，规则列表显示出口组名称并列出实际出口节点，不用第一台出口主机替代组名。

## 中转模式

配置两台或以上中转后，可在链路编辑器中选择中转模式：

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| 链路中转 | 流量按顺序经过每一台中转 | 固定路径、指定出境线路 |
| 主备 | 每条连接只用一台中转，坏了才换下一台（2.3.454 前叫「故障转移」） | 中转可用性优先 |
| 单连接叠加 | 单条连接拆分到全部中转并行传输（2.3.454 前叫「带宽叠加」） | 单条中转带宽不够用 |

### 单连接叠加 {#带宽叠加}

单连接叠加把**一条**客户端连接拆分到全部中转同时传输，由出口按序重组，因此单条连接的可用带宽接近各中转之和，而不是受限于其中最慢的一条路径。三台 100 Mbps 中转在理想情况下可以让一条连接跑到接近 300 Mbps。

工作方式：

- 入口给每个数据块编号，然后交给**最先空闲**的中转发送。快的中转自然承担更多数据块，不需要手动配置权重，实际分配比例会跟随各条线路的真实带宽变化。
- 出口按编号顺序重组后再写给目标，字节流与单路传输完全一致，应用层无感知。
- 单条中转中断时，它手上未送达的数据块交给其他中转重发，出口按编号去重，会话继续；全部中转都中断才会结束会话。
- 中转本身不需要改动，仍然是透明转发，多路径协议只在入口和出口之间生效。

前提条件：

- 仅 NEX 隧道支持，GOST 与 Nginx Stream 传输无法拆分单条连接。
- 至少两台中转，且入口、中转和出口的 Agent 都需要 v2.2.194 或更高版本。
- 实际能叠加的是**入口到出口**这一段。如果瓶颈在客户端到入口，或出口到目标，叠加中转不会提升速度。
- 各条线路延迟差异越大，出口重组时的缓冲越多；面板会限制缓冲上限并对过快的线路施加背压，避免内存增长。

2.3.411（FXP 2.2.126）起的几处改动直接影响叠加能跑到多少：

- **小块合并**：数据块的大小取决于一次从目标或客户端读到多少，读得勤时常常只有一两 KB，而窗口和重组缓冲都是按块数记的，小块时整个窗口只有一两 MB，200 ms 往返的线路就被钉在几十兆。现在中转都忙着的时候，后面的写并进队尾还没被领走的那一块，凑到 64 KiB；中转空着时照旧立刻发走，小流量不多等。
- **单条中转的在途上限从 16 MiB 提到 32 MiB**：在途除以往返时间就是这条中转的速率上限，200 ms 的线路上 16 MiB 封顶约 640 Mbps，千兆中转跑不满。
- 多路径只叠加入口到出口这一段；客户端到入口那一跳仍是一条 TCP，瓶颈在它时要配合[客户端侧的带宽叠加](./failover.md#bandwidth-aggregation)。

2.3.458（FXP 2.2.135）起：

- **断了的那一路自动补回来**：以前一条叠加连接里某一路断了（中转重启、线路抖一下），剩下几路照样跑，但断的那一路不会再回来，长连接一抖就慢到底。现在入口隔一秒去重拨那一路，拨通就接回同一条连接继续分数据。中转还没好时不会每条连接都去撞它：同一时刻只放一条连接去试，试通了大家一起补上。
- **一开始就按带宽分**：每一路带上那台中转在主机设置里填的「线路带宽」，连接刚开始、还没测出实际速度时就按它分（500M 和 300M 两台按 5:3）；跑起来以后按实测分。没填带宽的照旧从一样大开始。
- **连接监控里看每一路**：隧道「···」→ 连接监控，顶上多一栏「每一路」：每台中转最近 5 分钟上下行各跑多少、占全部的百分之几、这段时间拨了几次成没成。

### 家庭叠加 {#家庭叠加}

单连接叠加拆的是入口之后那一段，所以入口自己的带宽就是上限：入口是一台 VPS 时，前置再多也叠不过这台 VPS。把入口搬回家里就没有这个问题 —— 家里一台常开的 Linux（软路由、小主机、NAS 都行，amd64 / arm64）当入口，一条连接从家里拆到几台前置，落地机拼回来：

```
手机 / 电脑 ──内网──▶ 家里那台 ──┬──▶ 前置 A ──┐
                               ├──▶ 前置 B ──┼──▶ 落地 ──▶ 目标
                               └──▶ 前置 C ──┘
```

入口只往外拨，家里那台不需要公网 IP、不用开端口，照常装 Agent 就行。

链路管理 → 隧道链路 → **家庭叠加**（管理员），选三样：

1. **家里的机器**
2. **落地**：落地机上的入站节点（订阅里那种）
3. **前置**：至少两台，旁边写着各自的线路带宽和合计

点「建好」，面板一次做完：

- 家里那台的「入口 IP」没填时，填上 Agent 报上来的内网 IP（订阅里节点的地址就是它）；
- 建一条 NEX V1 隧道：跳点「家里 → 前置… → 落地」，中转方式「单连接叠加」；
- 建一条规则挂在这条隧道上，目标是落地节点自己的地址和端口，不用专属域名。规则自动认出这个落地节点，订阅里就多一个「家里 → 落地」的节点。

注意：

- 这个节点的地址是内网 IP，**只在家里的网络里能连**；出门在外用原来的节点。
- 家里的上行和下行都会经过家里那台机器：下载时它要收几台前置一起送来的流量，网卡和 CPU 要跟得上（千兆网卡就是 1G 封顶）。
- 只叠 TCP；UDP（比如游戏、QUIC）照常走一路。

### 单连接多路并发（没有并排中转时）

跨境线路经常按**单条 TCP 连接**限速，或者丢包让单条连接的窗口起不来：一条下载只跑几十 Mbit/s，开十条连接加起来却能跑满。带宽叠加靠的是几台并排的中转；没有中转（入口直连出口）或者中转是串成一条链的隧道，可以用 **单连接多路并发**：

在隧道卡片的菜单里点「多路并发」，选每条连接拆成几路（2 / 3 / 4 / 6 / 8）。入口把每条客户端连接拆成小块，从几条并行连接同时发到出口，出口按序号拼回去 —— 用的是和带宽叠加同一套多路会话（重组、丢腿重传、乱序缓冲都一样），目标看到的数据和单路一模一样。

- 只对 NEX V1 隧道有效；V2（WireGuard）外层只有一条 UDP 流，拆了没用。中转「主备 / 单连接叠加」的隧道不用再开，多出口负载均衡的隧道不能开（重组必须在同一个出口）。
- 只拆 TCP，UDP 照旧。改了之后新连接生效，正在传的连接不受影响。
- 路数不是越多越好：线路没有按连接限速时，多拆只多一点头部开销。一般 2–4 路就够。
- 需要入口 Agent **2.2.231** 或更新，中转和出口 2.2.194 起。版本不够时这条隧道照常按单路下发（每条客户端连接各走各的连接），不报错、不断流，升级之后下一次心跳自动生效；保存时会提示哪几台还要升级。

### 传输层自动调优

FXP 2.2.126 起，每条 NEX 隧道连接都会自动做两件事，不需要配置：

- **逐连接 BBR**：FXP 自己拨出和接受的每一条 TCP 连接都单独设成 BBR（系统默认是 cubic / reno、内核有 bbr 时）。安装脚本改的系统默认只在装 Agent 那一刻生效，Docker 里不改宿主 sysctl、内核当时没装 tcp_bbr 模块、或者后来又改回去了，隧道就会跑回 cubic —— 跨境线路丢一两个百分点，cubic 的窗口就起不来，现象是「带宽跑不满、速度忽高忽低」。用户自己选的其他算法（bbr2、bbrplus 等）不会被覆盖。
- **加密算法协商**：隧道两端握手时各报一声自己能用、偏好什么。有 AES-NI / ARMv8 加密扩展的机器保持 AES-256-GCM；虚拟 CPU 不露这些指令的机器（QEMU 的 qemu64 / kvm64 机型、一些嵌套虚拟化）上 AES-GCM 每核只有几十 MB/s，一条千兆线路只能跑出几百兆、中转上再减半，这类机器会偏好 ChaCha20-Poly1305（每核一两个 GB/s），另一端跟着用。偏好按启动时实测决定，不看 CPU 标志位。旧版本 FXP 不认识这两个字段，照旧 AES-256-GCM，互通不受影响。

两项都可以用环境变量强制（写进 Agent 的 systemd 单元，FXP 是它的子进程）：`FORWARDX_FXP_TCP_CONGESTION=bbr|cubic|off`、`FORWARDX_FXP_AEAD=aes-gcm|chacha20-poly1305`。FXP 的启动日志会打印实测的两种算法速度和最终的选择。

NEX V2 隧道（用户态 WireGuard）在 Agent 2.2.209 起按批收发：协议栈里排着的包一次最多 128 个交给 WireGuard，再经 UDP GSO 一次系统调用发出，对端按 GRO 一批收回。千兆以上的 V2 隧道 CPU 大头正是每包一次的系统调用和加密调度。

## 状态

| 状态 | 含义 |
| --- | --- |
| **已启用** | 隧道配置已打开 |
| **运行中** | 当前角色所需运行时和监听已就绪 |
| **可用** | 最近一次独立隧道探测通过 |

没有新鲜探测时，界面根据必经主机和可选出口的在线状态判断基础可用性。

隧道状态不与引用它的转发规则数量或运行状态绑定。多出口中至少一个出口探测成功时，整体可保持可用，失败出口在分支明细中单独展示。

界面按隧道类型显示 PROXY Protocol、TCP Fast Open、流量倍率、主备线路和传输参数。TCP Fast Open 仅在 NEX 隧道的受支持路径提供；Realm 的旧 `fast_open`/`zero_copy` 选项不再生成。未显示的参数不受当前类型支持。

### 链路整形

两端之间有硬限速时用：腾讯云联网的地域间带宽、各家云的公网带宽上限都是令牌桶限速器，超额的包直接丢。一条 BBR 流会一直探到上限之上，拿 4% 左右的重传换接近上限的速率；几条流一起探就互相把对方打掉，合计只有上限的六成，还逐秒抖。隧道里每条用户连接都是一条 TCP 流，所以多连接的下载看起来就是「跑不满、不稳定」。链路整形让 FXP 把往一个方向发的所有隧道帧合起来压在限速点之下：限速器不丢包，没有重传和回退，多少条连接合计都贴着上限跑，而且稳；排队发生在 FXP 进程里，TCP 在途量保持在 BDP 附近，加载时延迟也不涨。小帧（交互流量）在队列不深时优先放行，不排在大块后面；每条 TCP 连接还会设内核的发包速率上限。

NEX 隧道的「传输优化」里有三档：

- **自动**（默认）：平时不整形，只看每条连接的 TCP_INFO。出现「发送端有积压 + 重传」就是撞上了限速器：重传 1% 以上一秒就认，0.3% 到 1% 要连续两秒。起点按最近三秒平均送达速率的最高值，然后每秒有重传就降 3%（重传超过 2% 降 6%）；还没碰到过丢包时每个干净的秒升 25%（起点偏低时几秒就补上来）；连续五秒干净就往上探，步子从 1% 逐轮翻倍到 10%，停在上次丢包点之下 1.5%，十五分钟后再探。降到不再丢包的那个速率就是限速点，FXP 记在本机（`/var/lib/forwardx-fxp`）并报给面板，重启、换机器都直接从它起步。隧道编辑页里能看到每台主机每个方向的状态：还没遇到限速 / 正在找 / 学到多少 / 暂停。如果从起点降了一半重传还在，那不是限速器而是随机丢包，放弃整形十分钟再看。
- **手动**：填入口 → 出口（上行）和出口 → 入口（下行）的上限（Mbit/s），至少填一个方向。FXP 从 96% 起步，按重传在 60% 到 100% 之间微调。值不用很准：填 iperf3 测出来的实际吞吐或购买的带宽都行。怎么测：「网络测试」里用「iperf3 客户端」的 **UDP 模式**，每条流速率留空（不限）或填一个明显高于预期的值，结果里 `receiver` 那行的速率就是限速点；正向测上行，反向测下行。
- **关**：不整形。

作用范围：这条隧道在这台机器上的 FXP 进程（入口、出口、中转各自整形自己发出的方向）。两条隧道共用同一段限速链路时各自整形。UDP 直连通道（mimic）不整形；V2 走用户态 WireGuard 的连接读不到 TCP_INFO，自动档不会触发，手动档照样整形。需要两端 Agent 2.2.212（自带 FXP 2.2.127）起，旧版本忽略这些设置。

### UDP 抗丢包

只作用于 NEX 隧道的 UDP 直连（游戏、语音、QUIC 这类 UDP 流量），TCP 流量不受影响，默认关。打开后，每一跳（入口 → 中转 → 出口，回程反过来）把同一会话发出的包按顺序 10 个一组，用 Reed-Solomon 算出冗余包另外发出去：每 5 个包 1 个，满组时多耗约 20% 流量。组里第一个包等了 8 毫秒还没凑满就先发，所以包很稀的时候一组可能只有一两个包，冗余包等于复制一份，流量最多翻倍，但这类流量本来就小。接收端丢了几个包，只要不超过收到的冗余包数，就当场还原，不用等对端重发；数据包本身照常立刻发出，不加延迟。

还原出来的是原来的密文，照样要过认证和重放检查，伪造的冗余包解不出东西。冗余包用单独的包头，旧版本 FXP 收到直接丢掉：隧道上有机器还没升级时照常通，只是那一段不纠错；回程方向只发给已经给我们发过冗余包的一端，不会把冗余包发给旧入口。需要 Agent 2.2.218（自带 FXP 2.2.131）起。FXP 每分钟在日志里打一行 `fxp udp fec stats`：发了多少组和冗余包、还原了多少个包、多少组缺得太多没能还原。

适合：晚高峰有明显随机丢包的跨境线路上跑游戏、语音。不适合：丢包主要是带宽限速器造成的线路（多发的流量会更早撞上限速），这种情况先用上面的链路整形。

修改隧道拓扑后，面板会生成新的拓扑标识；旧拓扑迟到的探测结果不会写入新图表。

## mimic UDP 混淆

mimic 在物理网卡使用 XDP ingress 与 TC egress，需要 Linux 6.1+ 内核；Agent 会在 XDP `native` 与 `skb` 模式之间自动回退。mimic 来自 [hack3ric/mimic](https://github.com/hack3ric/mimic)（GPL-2.0-only，v0.7.1）：

- V1 对 FXP UDP 承载应用 `remote/local` filter。
- V2 对 WireGuard 外层 UDP 端口应用 filter。
- 多跳和额外出口按每条物理链路分别配置。
- TCP 通道保持原路径，不会因开启 UDP 混淆改为 mimic。

参与节点必须安装 `mimic`/`mimic-dkms`。面板优先使用主机中配置的网卡，否则使用 Agent 上报的默认路由网卡。缺环境时面板会显示 Agent 返回的原因，并在隧道编辑里按参与主机给出「安装 / 修复 mimic」按钮（Agent 2.2.223 起）：面板把安装脚本下发给 Agent 在机器上跑，进度和日志回到页面上。内核升级后模块没跟上时，Agent 会先自己用 DKMS 重编一次。

## 创建后检查

1. 确认所有链路节点 Agent 在线。
2. 检查每跳连接地址、承载端口和防火墙。
3. 运行链路测试并查看具体失败分支。
4. 查看 Agent 日志（`/var/log/forwardx-agent/`）中的运行时应用、监听和握手错误。
5. 只有 UDP 异常时，分别测试原生 UDP、V1/V2 承载和 mimic 配置，避免把 TCP 可达当作 UDP 已通。
