# 落地主机与 Shadowsocks 出口

普通的端口转发是入口机自己去连目标，目标看到的来源 IP 就是入口机。给规则设一个 **Shadowsocks 出口** 之后，入口机不再直接连目标，而是经 Shadowsocks 让另一台服务器（「落地」）代为连接：流量从落地出去，目标看到的是落地的 IP。

```text
客户端 ──▶ 入口机:端口（gost 监听，计数、限速都在这里）
              │  Shadowsocks（加密）
              ▼
          落地 SS 服务器 ──▶ 目标
```

出口有两种来源：

- **落地主机（Shadowsocks）**：面板管理的另一台主机，上面开着一个 Shadowsocks 落地入站（「落地入站」页面里那种 sing-box 节点）。没有的话可以在规则编辑器里 **一键创建**。
- **外部 Shadowsocks 链接**：粘贴一条别处的 `ss://` 链接，例如你在别家买的落地。

::: warning 需要的 Agent / 运行时版本
出口由 **入口机** 上的 Agent 下发给 gost。

- **TCP 出口（aes-256-gcm / aes-128-gcm / chacha20-ietf-poly1305）**：入口机 Agent 2.2.226 或更新。
- **UDP 走出口（协议 TCP+UDP）、SS2022 出口**：入口机 Agent **2.2.227** 或更新，并且它装着的 gost 运行时是 **3.2.6-nex3** 或更新。Agent 会实测运行时的版本（`forwardx-runtime -V`）并上报能力，面板以上报为准。升级 Agent 时安装脚本会一起把运行时换成面板带的最新自编版（2.3.448 起是 nex4，失败会回滚，见下文）。

条件不够时，不能给这台机器的规则设这样的出口；已经设了的规则按停用下发（不会退回直连，UDP 也不会绕过出口直连），规则卡片显示「需要升级 Agent」或「UDP 出口需要升级 Agent/运行时」「SS2022 出口需要升级 Agent/运行时」。落地主机不需要升级。
:::

## 什么时候用它，什么时候用隧道

| | Shadowsocks 出口 | 隧道 |
| --- | --- | --- |
| 落地要装什么 | 落地上只要有一个 Shadowsocks 服务端：面板管的主机一键开，或者用别家的 `ss://` | 落地也必须是面板管理的主机（装 Agent） |
| 能用别家的落地吗 | 能（外部链接） | 不能 |
| 协议 | TCP 或 TCP+UDP（TCP+UDP 时 UDP 也走出口，入口机要 Agent 2.2.227 + 运行时 nex3） | TCP / UDP |
| 多出口、负载均衡、线路组 | 不支持，一条规则一个出口 | 支持 |
| 适合 | 「想让目标看到某台机器的 IP」：解锁流媒体、固定出口 IP、借用现成的 SS 落地；DNS、QUIC、游戏这类 UDP 也能走 | 加密中转、多跳、多出口 |

两者也能叠在一起用：隧道负责线路，出口负责落地 IP，见下面的「隧道规则接出口」。

## 隧道规则接出口

面板 2.3.465 起，走 **NEX 隧道或 GOST 隧道**（包括「叠加」）的规则也能设出口：

```text
客户端 ──▶ 入口机 ──隧道──▶ 隧道出口机（本机的 SS 客户端）──Shadowsocks──▶ 落地 ──▶ 目标
```

隧道照常跑，线路质量由隧道负责；到了隧道出口机后不直接连目标，而是经 Shadowsocks 让落地代连，目标看到的是落地的 IP。适合「隧道走优质线路到香港，再从某个解锁落地出去」这类用法。

- **SS 客户端跑在隧道的出口机上**（多跳时是最后一跳；开了负载均衡的多出口时每台出口各跑一个）。所以上面说的 Agent / 运行时版本、UDP / SS2022 能力，查的是**隧道出口机**，不是入口机。
- 落地主机不能是隧道出口机自己；外部链接也不能指向隧道出口机。
- **Nginx 隧道不能接出口**；线路组照旧不能和出口一起用。
- 规则刚建好、出口机还没算好时，这条规则先不下发（几秒到下一次心跳），**绝不会先直连目标**。
- 规则的延迟测的是隧道出口机到落地这一段。

## 在规则里设置出口

在 **转发规则 → 添加 / 编辑规则** 里，选「端口转发」「隧道转发」或「叠加」之后，表单里有一节 **出口**（隧道规则见上一节）：

| 选项 | 说明 |
| --- | --- |
| 直接连接 | 默认。入口机自己连目标 |
| 落地主机 | 选一台落地主机，再选它上面的 Shadowsocks 入站 |
| 外部 SS 链接 | 粘贴 `ss://` 链接 |

选了出口之后，表单会自动做这几件事（因为出口是 gost 的转发链实现的）：

- **转发工具用 gost**。直连主机的规则直接切到 gost。用「端口转发」资源时，资源是 iptables / nftables / realm / socat / nginx 也能选出口：这些工具不会 Shadowsocks，开了出口的**这一条**规则下发时自动改用 gost 跑（端口、计数、限速照旧），库里记的工具不变，同一个资源上的其它规则不受影响；改回「直接连接」就恢复原来的工具（面板 2.3.451 起）。
- **协议决定 UDP 走不走出口**（2.3.460 起，以前是单独一个「UDP 也走出口」的勾）：选 TCP 只转 TCP；选 TCP+UDP，UDP 也经 Shadowsocks 从落地出去。开了出口时没有「只 UDP」。只有每一台入口机都报了 UDP 能力时才能选 TCP+UDP，否则它是灰的，出口那一段写着是哪台机器、要升级什么。不会出现「TCP 走出口、UDP 偷偷直连」。
- **线路组关闭**：出口本身就是固定的落地。

保存时面板会检查：

- 落地主机要在线（只在新选 / 换落地时检查；已经设好的规则改名字不受影响）；
- 落地主机不能是这条规则的入口主机（包括端口转发资源里的每一台入口）；
- 落地入站必须是 Shadowsocks、启用着、加密方式能做出口；
- 外部链接里的服务器不能是入口主机自己；
- 协议选了 TCP+UDP（UDP 走出口）、或者用 SS2022 出口时，每一台入口主机都要报了对应的能力（Agent 2.2.227 + 运行时 nex3）。

规则卡片上会显示 **「经 落地主机 东京 出口」** 或 **「经 外部 SS 出口」**（UDP 确实在走出口时后面加「（含 UDP）」；外部 SS 链接写成「（含 UDP，需对端支持 UDP）」——别人家的服务器开没开 UDP 中继，面板查不到），后面跟状态：

| 状态 | 意思 |
| --- | --- |
| 运行 | 出口配置正常，已下发 |
| 落地离线 | 落地主机的 Agent 掉线了。规则照样下发（落地上的 Shadowsocks 可能还活着），但请检查落地 |
| 需要升级 Agent | 入口机的 Agent 低于 2.2.226，规则没有下发 |
| UDP 出口需要升级 Agent/运行时 | 规则让 UDP 走出口，但入口机现在没有这项能力（Agent 低于 2.2.227、运行时不是 nex3、或者运行时升级失败被回滚了）。规则整条没有下发：TCP 不通，UDP 也不会直连。升级入口机，或者把协议改成 TCP 只走 TCP |
| SS2022 出口需要升级 Agent/运行时 | 出口用 SS2022，入口机没有这项能力，规则没有下发。升级入口机，或者换成经典 AEAD 的入站 / 链接 |
| 落地入站已删除 / 已停用 | 出口用的入站没了或被停用，规则没有下发 |
| 加密方式不支持 | 入站或链接的加密方式不能做出口，规则没有下发 |
| 出口配置失效 | 例如外部链接无法解密（面板迁移到了新服务器），请重新粘贴链接 |

## 一键创建落地 SS 入站

选了落地主机、而它上面还没有能做出口的 Shadowsocks 入站时，出口一节会出现 **「一键创建落地 SS 入站」**：

- 加密方式 `aes-256-gcm`，随机密码；
- 端口从落地主机的端口范围里挑一个空闲的（没设范围时在 20000-30000 之间挑）；
- 走的是「落地入站」页面的同一条新建流程：权限、额度、端口冲突检查一样不少；
- 打上「落地出口」标记：**它派生的节点默认不进客户端订阅**。管理员想把它也给客户端用，在订阅里打开这个节点即可。

谁能一键创建：管理员，或者这台主机的主人（还需要有客户端订阅权限）。

谁能拿落地入站当出口：

- 管理员：任意 Shadowsocks 落地入站；
- 普通用户：自己的落地入站；或者管理员开的「落地出口」入站，并且有这台落地主机的使用权限（和直连规则同一套主机授权）。别人的普通落地节点不能用 —— 那个端口的流量记在它的主人头上。

落地入站 **轮换密码、改端口** 之后，依赖它的规则自动跟上（每次下发都从入站现取凭据），入口机会被立刻通知重算。正在被当作出口的入站 **不能删除**，也不能改成别的协议或出口不支持的加密方式：面板会列出依赖它的规则，请先把这些规则的出口改掉。

## 外部 Shadowsocks 链接

支持 SIP002（`ss://base64(方法:密码)@主机:端口#名字`）和老式的整段 base64 两种写法。

- 加密方式支持 `aes-256-gcm`、`aes-128-gcm`、`chacha20-ietf-poly1305`，以及 `2022-blake3-aes-128-gcm`、`2022-blake3-aes-256-gcm`（SS2022 要入口机有能力，见下文；密码是单用户的 base64 密钥，`iPSK:uPSK` 多用户写法不支持；`2022-blake3-chacha20-poly1305` gost 不支持）；
- 不支持带插件（`plugin=obfs-local`、`v2ray-plugin` 等）或带 ws / grpc 传输的链接；
- 普通用户可以在自己的规则上使用外部链接；目标地址的限制和普通规则一样（内网 / 环回目标要求入口主机是自己的）。经别人的落地主机出口时，目标还必须是公网地址。

::: danger 安全提示：链接里的密码由面板保存
外部链接解析后的服务器、加密方式和 **密码** 会保存在面板的数据库里，用面板密钥（`JWT_SECRET` 或数据目录里的 `jwt.secret`）派生的 AES-256-GCM 加密，界面上只显示打码后的样子（`ss://aes-256-gcm:******@主机:端口`），接口也从不返回密文。数据库被拖走时拿到的只是密文；但能接触到面板密钥的人（服务器管理员）可以解出密码。不要粘贴你不愿意交给面板管理员的链接。

面板迁移到另一台服务器、且两边的面板密钥不同时，旧密文解不开，规则会显示「出口配置失效」并按停用下发，重新粘贴一次链接即可。
:::

## UDP 和 SS2022 说明

出口用的是随 Agent 下发的 gost 运行时（gost 3.2.6）里的 Shadowsocks 客户端。我们拿它对着落地入站用的 sing-box 1.14.0 逐项实测过（测试脚本在仓库的 `gost-runtime/test/ss-egress-e2e/`）：

| | 上游 gost / NEX 运行时 nex2 | NEX 运行时 3.2.6-nex3 起 |
| --- | --- | --- |
| 经典 AEAD 的 TCP | 互通 | 互通 |
| 经典 AEAD 的 UDP | **不通**（gost 收不到回包） | 互通 |
| SS2022 的 TCP | **不通**（回程解不出来） | 互通 |
| SS2022 的 UDP | **不通**（sing-box 验不过包） | 互通 |

nex3 修的是 gost 自己的几处 bug（UDP 会话的存取用了两个不同的键、回包里的地址没剥、过短的伪造回包能让运行时崩溃；防重放过滤器误判率过高，UDP 长跑会持续丢回包；SS2022 的会话密钥字节序错、TCP 回程头解析错），详见 `gost-runtime/nex-ssu.patch`、`nex-shadowsocks2.patch` 开头的说明。nex4（面板 2.3.448）再按 SIP022 校验 SS2022 的 UDP 回包：必须是服务端发的、带回本会话的 ID、包号没出现过，截获的回包不能再被重放进别的流；能力门槛仍是 nex3。实测覆盖了 UDP 回声（1~1472 字节）、经出口的 DNS 解析、QUIC 握手和多流数据、200 个并发 UDP 流、10 分钟持续 UDP 和空闲后恢复。

所以：

- 入口机是 Agent 2.2.227 + 运行时 nex3 时，协议可以选 TCP+UDP（UDP 走出口），SS2022 的落地入站 / 链接可以选；
- 入口机条件不够时，这两样不能选；已经设好的规则在它上面按停用下发，不会出现「显示在走出口、其实 UDP 直连了」；
- 一键创建的落地入站仍然默认用 `aes-256-gcm`：所有入口机都能用。需要 SS2022 时在「落地入站」页面开一个 SS2022 入站再选它。

### 运行时升级和回滚

升级入口机的 Agent 时，安装脚本会把运行时一起换成面板带的最新自编版（装着的 NEX 自编版比它旧就换，2.3.448 起是 nex4）：

1. 新文件先在旁边自检（`-V` 能跑、版本对），通过才替换，旧文件留成 `/usr/local/bin/forwardx-runtime.prev`；
2. 替换后重启正在跑的运行时服务，3 秒后没起来就当场换回旧文件；
3. Agent 启动后接着盯一会儿：新运行时自检失败，或者有规则要它跑、服务 90 秒内没起来，也会换回旧文件并重启。机器太忙、`-V` 超时不算失败，不会因此回滚；
4. 升级还没确认、服务又没在跑的这段时间，Agent 先不报 UDP / SS2022 能力。

回滚之后 Agent 上报的运行时版本是旧的、能力为空，面板据此把 UDP / SS2022 出口的规则按停用下发，卡片显示「UDP 出口需要升级 Agent/运行时」。经典 AEAD 的 TCP 出口不受影响。面板只有官方 gost（发版时自编版没编出来）时，Agent 也会如实报「没有能力」。

老式 AEAD 有已知的主动探测手段，SS2022 在这方面更好；如果落地需要直接给客户端用，建议给客户端另开一个 SS2022 入站。

## 流量、计费和限速

- **规则的流量统计、按量计费、限速和普通 gost 规则完全一样**：计数挂在入口机的监听端口上，限速是 gost 服务上的限速器，都在入口这一侧。
- 落地主机那边：一键创建的落地入站有自己的端口流量统计（「落地入站」页），经出口的流量也会记在那里；落地主机的机房流量当然也会增加。
- 入口机到落地这一段是 Shadowsocks 加密的；落地到目标这一段和直连一样是明文（目标本身是 HTTPS 的话照样是 HTTPS）。

## 排障

| 现象 | 处理 |
| --- | --- |
| 卡片显示「需要升级 Agent」 | 在主机列表里升级入口机的 Agent 到 2.2.226 或更新 |
| 卡片显示「UDP 出口需要升级 Agent/运行时」 | 升级入口机的 Agent 到 2.2.227 或更新（运行时会一起升到 nex3）。升级后仍然这样，看主机上 `/var/log/forwardx-agent/agent-go.log` 里的 `gost runtime self-check` 一行：运行时版本、能力，以及有没有回滚和原因 |
| UDP 走出口但不通 | 检查落地的 Shadowsocks 服务端是否开着 UDP、防火墙 / 安全组是否放行了落地入站的 **UDP** 端口 |
| 卡片显示「落地离线」 | 检查落地主机的 Agent 和网络；Shadowsocks 服务本身可能还在跑 |
| 规则运行但连不上目标 | 检查落地主机的防火墙 / 安全组是否放行了落地入站的 TCP 端口；在落地上确认它能访问目标 |
| 删除落地入站时报错 | 报错里列出了依赖它的规则，把这些规则的出口改成其他方式或删掉规则 |
| 外部链接报「不支持」 | 换一条用 `aes-256-gcm` / `aes-128-gcm` / `chacha20-ietf-poly1305` / `2022-blake3-aes-*-gcm`、不带插件的链接 |
