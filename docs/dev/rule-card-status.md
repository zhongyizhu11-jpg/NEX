# 规则卡的红 / 橙 / 绿怎么来的

2026-11-26 用户面板上出现了两种对不上的情况：

- 诊断能通的规则，卡片却一直红；
- 诊断不通的规则，卡片却是绿的。

当时的背景：高防目标 `hkboil.ddos.top` 一直拦着 jinx(39.9y)、Jinx(29.9y) 两台出口，只有 hep ix 能通。
这份记录把整条链路理一遍：数据从哪来、在哪几处缓存、最后怎么定颜色，以及这次修掉了哪几处。

端到端：`server/liveEndToEnd.sqlite.test.ts`（上报 → 推送 → 卡片重取到新数），浏览器那段 `node scripts/live-browser-check.mjs`（要先 `npm run dev:panel`）。

场景矩阵测试见 `server/ruleCardScenarios.test.ts`，每个场景都是面板上真实出现过的情况（场景 8、9 是 2.3.557 补的：在用出口自己超时 / 刚切换）。

## 一、数据从哪来

一张负载均衡规则的卡片，用到四份数据：

| 数据 | 谁测 | 多久一次 | 存在哪 |
|---|---|---|---|
| 规则定时端到端探测 | 出口机 TCPing 目标；记进规则那条记录的是**此刻在用的那台**（2.3.555 起，以前固定是主出口）。2.3.557 起「附加：检查出口到目标」关着（默认）时**只有在用的那台**去探，开着时每台都探 | 约 1 分钟 | 内存 `ruleLatencyView` 规则样本（每次上报都写）；数据库 `tcping_stats`（历史，约 5 分钟一条，状态变了立刻写） |
| 入口 → 每台出口 | 入口机 TCPing 出口的隧道监听口 | 约 1 分钟 | 面板内存 `ruleLatencyView` |
| 每台出口 → 目标 | ① 出口机定时 TCPing ② 出口机快速探测（只在「附加：检查出口到目标」开着时，2.3.557） | ① 约 1 分钟；② 几秒（按「检测与切换」） | 面板内存（① `ruleLatencyView`，② `exitTargetHealth`） |
| 入口在用哪台出口 | 入口 Agent / FXP 上报 | 状态一变 1 秒内，平时 10 秒 | 面板内存 `balanceLive` |

不是负载均衡的规则，只有第一份。

**内存是「现在」，数据库是「历史」（2.3.559）**：Agent 状态没变也每轮（约 1 分钟）都报；面板每次上报、每次诊断都更新内存里的规则样本和链路样本，
数据库那边照旧按闸门约 5 分钟写一条历史（延迟记录、30 天色块用）。以前两边都按 5 分钟节流，卡片上的数最多停在 5 分钟前，
诊断测完卡片也不变（用户：「诊断延迟返回后，规则还显示 7ms 8 分钟前」）。面板刚重启、内存还空着时才退回数据库最新一条。

## 二、服务端怎么拼

`withLiveRuleStatus`（`server/ruleLiveStatus.ts`）是唯一拼规则「现在」状态的地方：规则卡、表格、订阅（按延迟排序、节点通不通）、
Telegram 都读它，不再各拼各的。分两步：

1. **读数据库**：字节数和最新一条定时探测 / 诊断。这一部分缓存 5 秒。
2. **补内存里的实时数据**（不缓存，每次请求都现算）：
   - **实时样本**（`withRuleLiveSamples`）：比数据库那条新就盖上去；转发组父规则的延迟是从成员拼的，不盖。
   - 失败种类、实时速率。
   - 负载均衡（`withRuleExitTargets`，`server/exitTargetHealth.ts`）：
   - **在用出口**：取入口实时上报里扛流量最多的一台；没有实时上报时，按快速探测估算。
   - **延迟**：取「入口 → 在用出口」加「在用出口 → 目标」的整链；两段都测到才写。
   - **在用出口已经被快速探测判成连不上目标**：写成超时，不拿它一分钟前那次成功的数写绿色（2.3.555）。
   - **两段还没测到、数据库最新那条超时是切换前别的出口测的**：不写超时，也不写数，来源记为 `live`，等这台测到。
   - **数据库最新那条超时就是在用这台自己测的**（2.3.557，`ruleRecordedProbe`）：照实写超时。快速探测也判它坏时入口几秒内会切走，橙色；
     没有快速探测说它坏（「只看出口组」不派快速探测），入口不会因为目标换走，流量就是过不去：`exitTargetOk` 记 0，红色，订阅里也算不通。
     以前不分是哪台测的，在用这台自己的超时也被当成「还没测到」，卡片绿着（用户面板 2026-11-27，场景 8）。
   - **几台连得上（`exitTargetOk`）**：入口报的不是 down、并且快速探测也没说连不上的台数（2.3.555）。
   - **卡片上那一句（`exitTargetNote`）**：写明哪台连不上、已经切走。

## 三、前端怎么定颜色

### 刷新

卡片每 **3 秒**刷新一次（2.3.555 之前是 15 秒）。页面切到后台时停。

### 前端不另存一份（2.3.559）

以前前端有两层「接着显示上一次的」：探测缓存（`ruleProbeCache`，按时间戳挑新旧）和浏览器本地的「上次状态」快照。
两层都删了：服务端这一次给的就是现在，刷新页面不会先闪几分钟前的颜色，也不会拿旧的盖掉新的。数据还没回来时显示加载骨架，不显示旧状态。

剩下唯一的一条：改了规则之后，比修改时刻旧的那次探测不显示（`Rules.tsx` 的 `ruleEditedAt`），等改完之后测的那一次。

### 定颜色（`resolveForwardRuleVisualStatus`，`client/src/lib/forwardRuleStatus.ts`）

2.3.558 起卡片上分两样看（用户：「只要是通的状态点都是绿色，指定的出口不通只是走势线颜色不一样就行」）：

- **状态点**（`ruleVisualHealth`，`client/src/features/rules/ruleFlow.ts`；卡片、深空行、表格三处画点都用它）：通就是绿，不通红，停用 / 还在等上报灰。
- **走势线**（卡片的色调：走势线、左上角那抹光、地址行的箭头）：「指定的出口连不上、已切到别的出口」时琥珀，提醒指定没生效。

从上往下，命中第一条就定下来：

| 条件 | 状态点 | 走势线 | 卡片上写什么 |
|---|---|---|---|
| 停用 / 授权失效 / 经过的主机离线 | 灰 / 红 | — | 原因 |
| 最新探测是超时，但还有出口连得上（`exitTargetOk > 0`）：在用的刚坏、入口正在切 | 绿 | 琥珀 | （悬停）在用的出口连不上目标，正在切走 |
| 最新探测是超时，并且没有一台能接住 | **红** | 红 | 最近一次端到端探测超时 / 失败原因 |
| 探测通，**指定的出口**连不上、已切到别的出口（`exitTargetNote` 有值 → `pinBypassed`） | 绿 | **琥珀** | 延迟（不写原因，用户：「卡片不用写」） |
| 探测通（含自动分配时某台出口坏了、流量在别的出口上照走） | **绿** | 正常 | 延迟 |
| 还没有探测：看托管监听有没有起来 | 绿 / 灰 | — | 运行中 / 等待确认 |

`exitTargetNote` 只在指定的出口对这条规则不能用时才有（2.3.558），前端只拿它当走势线的开关，不显示这句。自动分配时哪台出口坏了，在负载均衡弹窗里看，卡片照常绿着。
「指定的是哪台」取入口心跳下发时实际生效的那一个（`server/tunnelPinState.ts`；指定的那台离线时不算指定）。

## 四、订阅「自动隐藏不通的节点」

这个开关默认开着。判断分两层：

1. **探测层面**：规则最近 15 分钟里，最新连续 3 次定时探测都超时，算不通（`getUnreachableRuleIds`）。
2. **负载均衡的规则**：定时探测是从主出口测的。只要还有一台出口连得上目标，就不算不通、不隐藏（`ruleHasReachableExit`，2.3.555）。
   以前主出口被拦就会连着超时，节点被从订阅里拿掉，可流量其实在别的出口上照常走（用户：「有时订阅又不通」）。

「按延迟排序」用的也是在用出口的整链，和卡片上的数一致。

## 五、诊断和卡片的关系

- 诊断（`rules.startSelfTest`）走**此刻在用**的出口，逐段测一遍。
- 卡片显示的是上面这几份数据拼出来的结果。

两者都看在用的出口，所以正常情况下只差几毫秒。诊断一完成就写进实时样本，卡片下一次刷新就是诊断测到的那个数。会对不上的只有一种情况：入口还没来得及切走的那几秒。
这时卡片是**橙色**（场景 4），不会再显示成绿色。

## 六、规则的「延迟记录」记哪台出口（2.3.555）

每台出口机每分钟都会探一次目标，但写进这条规则自己那条记录的，只有一台：

- **以前**：固定写主出口的。主出口被高防拦了，记录里就全是超时，可流量其实在别的出口上照常走。
  卡片、「延迟记录」图、订阅自动隐藏读的都是这条记录，三处一起错。
- **现在**：写**此刻在用的那台**（`ruleRecordingExitHostId`）。先看入口实时上报里扛流量最多的那台；没有实时上报时按快速探测估；都不知道才是主出口。
  隧道那一段也换成「入口 → 这台出口」的探测（每台出口一条分支），这样整链才是同一条路径上的两段。

在用的出口切换时，这一分钟可能多记一条或少记一条，不影响判断。
