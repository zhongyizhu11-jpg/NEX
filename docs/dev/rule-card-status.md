# 规则卡的红 / 橙 / 绿怎么来的

2026-11-26 用户面板上出现了两种对不上的情况：

- 诊断能通的规则，卡片却一直红；
- 诊断不通的规则，卡片却是绿的。

当时的背景：高防目标 `hkboil.ddos.top` 一直拦着 jinx(39.9y)、Jinx(29.9y) 两台出口，只有 hep ix 能通。
这份记录把整条链路理一遍：数据从哪来、在哪几处缓存、最后怎么定颜色，以及这次修掉了哪几处。

场景矩阵测试见 `server/ruleCardScenarios.test.ts`，每个场景都是面板上真实出现过的情况。

## 一、数据从哪来

一张负载均衡规则的卡片，用到四份数据：

| 数据 | 谁测 | 多久一次 | 存在哪 |
|---|---|---|---|
| 规则定时端到端探测 | 主出口机 TCPing 目标 | 约 1 分钟 | 数据库 `tcping_stats` |
| 入口 → 每台出口 | 入口机 TCPing 出口的隧道监听口 | 约 1 分钟 | 面板内存 `ruleLatencyView` |
| 每台出口 → 目标 | ① 出口机定时 TCPing ② 出口机快速探测 | ① 约 1 分钟；② 几秒（按「检测与切换」） | 面板内存（① `ruleLatencyView`，② `exitTargetHealth`） |
| 入口在用哪台出口 | 入口 Agent / FXP 上报 | 状态一变 1 秒内，平时 10 秒 | 面板内存 `balanceLive` |

不是负载均衡的规则，只有第一份。

## 二、服务端怎么拼

`rules.trafficSummary`（`server/routers/rules.traffic.ts`）分两步拼卡片数据。

1. **读数据库**：字节数和最新一条定时探测。这一部分缓存 5 秒。
2. **补内存里的实时数据**：`withRuleExitTargets`（`server/exitTargetHealth.ts`）。这一步不缓存，每次请求都现算：
   - **在用出口**：取入口实时上报里扛流量最多的一台；没有实时上报时，按快速探测估算。
   - **延迟**：取「入口 → 在用出口」加「在用出口 → 目标」的整链；两段都测到才写。
   - **在用出口已经被快速探测判成连不上目标**：写成超时，不拿它一分钟前那次成功的数写绿色（2.3.555）。
   - **两段还没测到，但入口报着它在用**：不写超时，也不写数，来源记为 `live`。
   - **几台连得上（`exitTargetOk`）**：入口报的不是 down、并且快速探测也没说连不上的台数（2.3.555）。
   - **卡片上那一句（`exitTargetNote`）**：写明哪台连不上、已经切走。

## 三、前端怎么定颜色

### 刷新

卡片每 **3 秒**刷新一次（2.3.555 之前是 15 秒）。页面切到后台时停。

### 探测缓存（`client/src/lib/ruleProbeCache.ts`）

这一层的作用是：这一行数据暂时缺席时，接着显示上一次的结果，不闪。

- 服务端按实时数据拼出来的结论（来源是 `panel`、`exit-target`、`live`），一律以这一次为准，不比时间戳（2.3.555）。
  这几份的时间戳来自不同的探测，不保证一直往前走。按时间戳挑，会让一条更早算出的「超时」顶掉服务端刚给的「通」。
- 来源是 `live`（不是超时、只是还没测到数）时，缓存里旧的那份直接作废。
- 规则自己的定时探测，照旧按时间戳防止乱序返回。

### 定颜色（`resolveForwardRuleVisualStatus`，`client/src/lib/forwardRuleStatus.ts`）

从上往下，命中第一条就定下来：

| 条件 | 颜色 | 卡片上写什么 |
|---|---|---|
| 停用 / 授权失效 / 经过的主机离线 | 灰 / 红 | 原因 |
| 最新探测是超时，但还有出口连得上（`exitTargetOk > 0`） | **橙**（确定） | 哪台连不上、已切走 |
| 最新探测是超时，并且没有一台连得上 | **红** | 最近一次端到端探测超时 / 失败原因 |
| 探测通，但有别的出口连不上或不稳 | **橙**（确定） | 哪台有问题 |
| 探测通 | **绿** | 延迟 |
| 还没有探测：看托管监听有没有起来 | 绿 / 橙 | 运行中 / 等待确认 |

### 上次状态（`preferLastKnownForwardRuleVisualStatus` + 浏览器本地快照）

用途：刚打开页面、数据还没回来的那一下，接着显示上一次的颜色，免得先闪一下橙色。

- 只在「还在等上报」的橙色时才拿上一次的颜色顶替。
- 「有出口连不上、已切走」也是橙色，但它是有实际数据的结论（`confirmed: true`）：照实显示，也照常写进本地快照（2.3.555）。
  以前它被当成「还在等上报」，结果用户面板上 hkt/3 一直显示上一次的红色，刷新也不变，诊断却是通的。

## 四、订阅「自动隐藏不通的节点」

这个开关默认开着。判断分两层：

1. **探测层面**：规则最近 15 分钟里，最新连续 3 次定时探测都超时，算不通（`getUnreachableRuleIds`）。
2. **负载均衡的规则**：定时探测是从主出口测的。只要还有一台出口连得上目标，就不算不通、不隐藏（`ruleHasReachableExit`，2.3.555）。
   以前主出口被拦就会连着超时，节点被从订阅里拿掉，可流量其实在别的出口上照常走（用户：「有时订阅又不通」）。

「按延迟排序」用的也是在用出口的整链，和卡片上的数一致。

## 五、诊断和卡片的关系

- 诊断（`rules.startSelfTest`）走**此刻在用**的出口，逐段测一遍。
- 卡片显示的是上面这几份数据拼出来的结果。

两者都看在用的出口，所以正常情况下只差几毫秒。会对不上的只有一种情况：入口还没来得及切走的那几秒。
这时卡片是**橙色**（场景 4），不会再显示成绿色。

## 六、还没做的

规则的「延迟记录」图里，混着主出口那条定时探测的超时。主出口被拦时，图上会有零星的超时点，但这条规则的流量其实是通的。
要把它拆开，需要按探测的来源（主出口 / 在用出口 / 诊断）分别存，属于数据库结构上的改动，留到下一步。
